## 2. 逐模块评估

### 模块一：本地资产解析与代码骨架生成

#### 1.1 OpenAPI/Swagger → RestAssured / pytest 骨架 —— 可做，4–6 人日

- **文档要什么**：导入本地 OpenAPI JSON/YAML → 生成 Java `RestAssured` 或 Python `requests/pytest` 测试类骨架（方法签名、请求 Path、参数占位、`statusCode(200)` 断言）。
- **现有什么**：请求模型 `ImportedRequest { name, group, method, url, headers, body, bodyType, rawContentType }` 已经定型并被 ApiClient 消费（`collectionImport.ts:27-37`）；`js-yaml` 已在依赖里（YAML 输入零成本）；`exceljs`/`xlsx` 也在，文件选择、预览、合并策略（`mergeRequests`：skip/overwrite/duplicate）全部现成。
- **差什么**：①OpenAPI 2.0/3.0/3.1 → 上述模型的解析器（`paths` × method、`servers`/`basePath`、`$ref`（含循环）、`parameters`（path/query/header）、`requestBody` schema → 示例 JSON、`security` → 占位头）；②两种语言的代码生成器；③入口（放在 ApiClient 的「导入」旁，或新的生成页）。
- **可行性判断**：**高**。纯 Node/渲染层纯函数，无新依赖。参考 `collectionImport.ts` 的写法（纯解析 + 页面只做预览/确认）即可复用其测试范式（该文件有 300 行单测）。
- **风险**：`$ref` 递归与 `allOf/oneOf` 是主要不确定性；生成的 Java 代码**不能编译就是废品** —— 但本应用有 CodeLab（真 javac/python），可以做成「生成 → 一键在 CodeLab 编译 → 通过才算生成成功」，这是同类工具做不到的闭环（见 §6.1）。
- **落点建议**：`src/utils/openapi.ts`、`src/utils/codegen/restassured.ts`、`src/utils/codegen/pytest.ts` + 各自单测。

#### 1.2 YAML 元素库 → Playwright POM —— 可做，3–4 人日

- **文档要什么**：在平台里（文档写「存 SQLite」）可视化维护页面元素名与定位器 → 一键生成 Java/Python 版 Page Object（构造方法、`page` 注入、`Locator` 定义）。
- **现有什么**：`useCollection` + `ws:get`/`ws:set` 的集合读写机制；`VAULT_COLLECTIONS` 加一个键就能新增集合，自动获得加密、备份、迁移、跨机器携带。
- **差什么**：新集合（如 `pomPages`）的结构与迁移、元素 CRUD 页、YAML 导入导出、两种语言的 POM 生成器。
- **可行性判断**：**高**，但文档的「存 SQLite」**必须改**（见 §3 ADR-1）。
- **风险**：定位器字符串里可能有引号/反斜杠 → 生成代码必须正确转义（否则生成的 Java 语法错误），这是必测项。

#### 1.3 JSON/DB → POJO / Pydantic —— JSON 部分可做，DB 直连建议不做

- **文档要什么**：①粘贴一段真实 JSON 响应 → 生成 Java POJO（带 Lombok）或 Python Pydantic/dataclass；②直连本地 MySQL 读表结构生成实体。
- **现有什么**：只有 `json-paths.js`（JSON 路径取值，2.9 KB），无类型推断；无 DB 驱动。
- **可行性判断**：
  - **① JSON → 模型：高**。纯逻辑，1.5–2 人日。要点：类型合并（同名字段多值取并集）、数组元素推断、`null` → 可选类型、命名策略（snake ↔ camel）、嵌套类命名冲突、Lombok 注解开关。可直接复用模块一.1 的生成器骨架。
  - **② DB 直连：不建议做**。需要 `mysql2`（新增依赖）+ 连接凭据管理（必须进 vault 加密，不能落明文配置）+ 用户本机连接公司库带来的合规不确定性。**替代方案**：让用户粘贴 `SHOW CREATE TABLE` 或 `information_schema.columns` 查询结果 → 走同一个生成器。功能等价、零依赖、零合规风险。

#### 1.4 断言模板库 —— 可做，0.5–1 人日（投入产出比最高）

- **文档要什么**：一个「断言字典」，按场景（REST 状态码 / JSON 结构 / Schema 校验 / Playwright 可见性 / 文本包含 / 属性比对）检索，一键复制 2–3 行代码片段。
- **现有什么**：`codeSnippets` 集合、CodeLab 页的片段管理、`useToolResult` 的「复制结果 / 导出」外壳、命令面板可搜片段（`CommandPalette.tsx:123-168`）。
- **差什么**：几乎是**纯数据**——内置种子片段（Java/Python 各一套断言模板）+ 按语言/框架分组的浏览视图 + 复制。
- **可行性判断**：**最高**。文档自己也说「这不算生成代码，这叫代码片段管理」，与本应用现有片段能力完全同构。
- **落点建议**：Toolbox 新增一个工具（或 CodeLab 加「断言库」页签），种子片段走静态 JSON，用户自定义片段走 `codeSnippets`。

### 模块二：压测引擎辅助与数据工厂

#### 2.1 接口定义 → .jmx 自动化生成 —— 可做，2–3 人日（本应用的最大优势项）

- **文档要什么**：读接口定义（Swagger/Postman）→ 配置线程组（并发、循环）、参数化 → 生成标准 `.jmx`，拿去 JMeter GUI 跑。
- **现有什么**：`buildJmxTemplate(url, method, threads, loops)` 已能从单个接口生成可校验的 `.jmx`（`jmx-script.js`）；`inspectJmx` 做静态检查（是否支持 `-Jthreads/-Jloops` 覆盖）；`ipc-jmeter.js` 能直接非 GUI 跑并解析 `.jtl`；脚本库（`ipc-jmxlib.js`）负责收纳、命名、默认参数、最近运行记录。
- **差什么**：从「单接口」到「**一批接口合成一个 ThreadGroup**」：多 HTTPSampler、`CSV Data Set Config`（对应模块 2.2 的 CSV）、`${__P(threads,10)}` 参数化、事务控制器/思考时间、断言（响应码）。
- **可行性判断**：**高，且是自然延伸**。文档设想「生成完拿去 JMeter GUI 跑」，本应用可以**生成后当场非 GUI 跑一遍**并给出错误率 —— 闭环更短。
- **风险**：JMX 的 `hashTree` 嵌套结构极易生成出「GUI 能打开、运行结果不对」的脚本。**验收口径必须是**：`inspectJmx` 通过 + 真跑一次且 `samples` 数等于预期（线程×循环×接口数），不是「文件生成了」。

#### 2.2 本地测试数据生成引擎（10 万条）—— 可做，1.5–2 人日

- **文档要什么**：不依赖外部服务，集成 Faker，批量生成 10 万手机号 / 身份证 / 中英文姓名 / 时间戳 → 导出 CSV/JSON 喂 pytest 参数化或 JMeter `CSV Data Set Config`。
- **现有什么**：**能力已经超过文档设想**——17 类生成器（手机号、身份证**含校验位**、统一社会信用代码、银行卡 Luhn、车牌、MAC、边界值、SQL 注入串、长文本等），6 种导出格式（含 SQL INSERT 与按类型分 Sheet 的 XLSX），生成结果可一键回填接口调试/压测。
- **差什么**：
  1. **量级**：`MAX_COUNT = 5000`（`DataGenerator.tsx:48`），且生成在渲染层同步执行 → 10 万条会卡死 UI；
  2. **落盘方式**：导出是把整个字符串在内存里拼好再写盘（`doExport` → `exportData` 返回 `{content}`），10 万行 CSV 约 10–20 MB 字符串，可行但会卡；
  3. 唯一性/去重约束、进度与可中断、与 JMeter CSV 的列名约定。
- **可行性判断**：**中高**。核心已在，缺的是「量」与「流式」。要新加一个主进程批量生成 IPC（分批生成 → 流式 append 写 CSV），XLSX 在 10 万量级**不可行**（exceljs 内存会炸），只支持 CSV/JSON/TXT 要有明确提示。
- **重要修正**：**不要引入 Faker**。现有生成器是自研且可校验的（身份证校验位、Luhn、USCC 都算对），第三方 Faker 生成的身证号大概率过不了校验位 —— 引入它等于能力倒退。

#### 2.3 MySQL 数据快照与清理 —— 建议不做直连

- **文档要什么**：测试前备份本地 MySQL 测试库，跑完还原或执行清理 SQL。
- **现状**：无 DB 驱动；有 SQL 片段库（`SqlSnippets.tsx`，1026 行）与参数化转换工具。
- **可行性判断**：技术上能做（`mysql2` + 导出 SQL/CSV + 还原），但**这是全文档唯一会直接改写用户数据库、且误操作不可恢复**的功能：
  - 「备份」大表要靠 `mysqldump` 或应用内 `SELECT *` 流式导出，后者对百万行表不现实；
  - 「还原」= 对真实库执行 DROP/INSERT，库名填错就是事故；
  - 凭据要落盘 → 必须进 vault 加密；本仓库是**公开仓库**，任何示例连接串都可能被当成模板抄走。
- **建议替代（成本近乎为零）**：保留 SQL 片段库，增加「清库/重置 SQL 模板」分类 + 冲突提示 + **只生成不执行**；若要执行，也只在用户显式标记为 dev 的库上执行，且执行前打印影响行数 + 二次确认 + 拒绝非 `dev_/test_` 前缀库名。
- **若坚持要做**：4–6 人日，且必须独立评审（安全维度）。

### 模块三：自动化代码质量「体检中心」（静态扫描）—— 可做，3–4 人日

- **文档要什么**：① UI 自动化反模式（硬编码 `sleep()`、绝对 XPath、深层 CSS、缺 `data-testid`）；② 接口测试代码（硬编码 URL/Token/DB 密码、断言只有 `status_code == 200`）；③ 依赖冲突（`pom.xml` / `requirements.txt`）。
- **现有什么**：无扫描 IPC，但有可复用的先例：目录遍历/白名单后缀（`ipc-cases.js`、`ipc-jmxlib.js`）、正则规则扫描（`scripts/check-privacy.js`，本来就是扫硬编码账号密码的，规则可移植）。**无任何 AST 解析依赖**。
- **差什么**：`scan:run` IPC（选目录 → 遍历（限深度/文件数/后缀白名单）→ 规则引擎（正则 + 行号 + 命中上下文）→ 分组结果）、规则定义表、结果表 UI（点击定位/复制）、`pom.xml` 与 `requirements.txt` 的依赖清单提取与冲突判定。
- **可行性判断**：**中高**。与文档「千万不要做 AST，就用变量替换/正则」的建议一致；`pom.xml` 用正则抓 `<artifactId>/<version>` 够用（不引入 XML 解析器）。
- **风险（主要风险是可信度）**：正则误报会让整个功能被弃用。必须：规则可单条开关、每条命中带行号与原文、报告页写明「启发式检查，非语法树分析」、给出「已知误报模式」。
- **安全**：扫的是用户本地仓库。本应用无云端上传，但要确保扫到的疑似密码**不写日志、不进导出**（与 `check-privacy.js` 同口径处理）。

### 模块四：测试资产看板与覆盖率台账

#### 4.1 接口/页面覆盖矩阵 —— 可做，2–3 人日

- **文档要什么**：解析 Apifox/Postman 集合（100 个接口），扫描代码里的请求路径（65 个），高亮未覆盖的 35 个。
- **现有什么**：已导入的接口集合（`apiRequests`）、真实调用历史（`apiHistory`）、回归集与运行结果（`regressionSets`/`regressionRuns`）——**「应该覆盖什么」这一半数据已经齐了**。
- **差什么**：扫描代码取路径（复用模块三的扫描器，规则如 `get("/api/x")`、`.url("/api/x")`、`requests.post(f"...")`）+ 路径归一（`{id}` / `:id` / `{{id}}` / baseURL 前缀）+ 覆盖视图。
- **可行性判断**：**中高**，但**价值取决于匹配率**。若代码里是常量拼装（`BASE + "/user"`），静态匹配会大面积漏判。
- **必须遵守的口径**：宁可给「无法判定」三态（已覆盖 / 未覆盖 / 无法判定），也不要给一个漂亮的假百分比。这套口径与 QA 侧的「覆盖率账本」一致。

#### 4.2 用例映射追溯 —— 降级做，2–3 人日

- **文档要什么**：维护本地 Excel 用例与代码方法的映射，防止「写了代码不知道测的是哪条需求」。
- **冲突点**：本应用用例库**明确不做内容解析**（`Cases.tsx:20-27` 的原话：「一旦开始解析，格式差异（xmind 版本、Excel 合并单元格）会变成无底洞」）。文档要求解析 Excel = 推翻既有设计决策。
- **建议**：拆成两层——①「映射表」：用例编号 ↔ 脚本文件/方法，手工维护，存集合，成本极低；②「CSV 导入」：只读规范化 CSV（`electron/csv.js` 已有解析器），不碰 xmind、不碰合并单元格。若后续确需 Excel，`exceljs` 已在依赖里，但要把「合并单元格/多 Sheet」的坑单独立项。

### 模块五：执行结果聚合与「失败聚类」

#### 5.1 Allure 报告二次加工 —— 可做，3–4 人日

- **文档要什么**：解析 `allure-results` → flaky 追踪（历史记录标记「一会儿过一会儿挂」）+ 失败聚类（15 个脚本同一 `TimeoutException` → 提示「疑似前置服务挂了」）。
- **现有什么**：无 Allure 解析；但**聚类算法已有先例**——Toolbox 的「日志分析」工具就是「按异常聚类，给出次数、首末时间与折叠堆栈」（`Toolbox.tsx:62`）。`allure-results` 是纯 JSON 目录（`*-result.json` / `*-container.json` / `environment.xml`），解析无难度、无新依赖。
- **差什么**：目录导入（`dialog.showOpenDialog` 选目录）、结果归一（用例全名/状态/耗时/重跑/附件）、历史落盘（新集合，如 `allureRuns`）、flaky 判定、聚类复用日志分析算法。
- **可行性判断**：**高**。
- **口径要求（必须写进实现说明）**：**flaky 不能由单份报告判定**——定义必须是「同一用例在 ≥N 次运行中既出现过 passed 又出现过 failed」，且要显示分母（跑了几次）。否则「重跑一次变绿」会被误报成 flaky，或真的 flaky 被漏掉。

#### 5.2 JMeter .jtl 结果分析 —— 可做，1 人日（全文档投入产出比最高）

- **文档要什么**：导入 .jtl → 图表（TPS、响应时间 90/99 线）+ 错误率最高的接口。
- **现有什么**：`parseJtl` **已经逐行解析** `.jtl`（`elapsed/success/code/label/timestamp`），并已算出样本数/错误数/错误率/均值（`jmeter-args.js` + `ipc-jmeter.js:443`）；`PerfTest` 页已有历史运行趋势小图（`JmxLibrary.tsx` 的 `jmxlib-trend`）。
- **差什么**：分位数（P90/P99）、TPS 时序曲线、按 `label`（接口）分组的错误率 Top N —— 全是给定行数组的纯计算。
- **可行性判断**：**最高**。数据管道已通，只缺指标与图表。建议作为 P0 第一项落地。

## 3. 必须先定的四项架构决策（ADR）

### ADR-1：不引入 SQLite，所有平台元数据存 vault 集合

- **决策**：新增的持久化（元素库、映射表、Allure 历史、覆盖台账）一律走 `VAULT_COLLECTIONS` + `ws:get`/`ws:set` + `schemaVersion` 迁移。
- **背景**：文档建议「直接上 SQLite，配置文件跟绿色软件一样」。但本应用的数据层是**单一加密 vault**，且已有备份、异地镜像、恢复快照、损坏自愈、数据目录迁移一整套链路（AGENTS.md「1.6.0/1.6.1 的约定」）。
- **备选与放弃原因**：
  - SQLite（`better-sqlite3`）= **原生模块**，要 `electron-rebuild`、要写 `asarUnpack`、要过本机「Low IL 完整性级别导致 exe 闪退」的历史坑；而且会让「备份/恢复」链路分叉（`backup:restore` 只认 vault 文件），用户换机器会丢元数据。
  - 明文 JSON 文件 = 违反本项目「一律加密落盘」的既有约束，且公开仓库里容易演变成隐私事故。
- **后果（含代价）**：查询能力弱于 SQL（全量数组在内存里过滤），几十万行级的台账会变慢。当前数据规模（接口数百、脚本数百、运行历史数百）完全够用；超过 10 万行要另做增量策略，届时再评估。

### ADR-2：不引入 Python/Java 后端，全部能力留在主进程

- **决策**：所有解析/生成/扫描都在 Electron 主进程用 Node 实现，不另起 FastAPI/Spring Boot 服务。
- **背景**：文档技术建议是 Python(FastAPI) 或 Java(Spring Boot) + SQLite。
- **备选与放弃原因**：另起服务意味着**两个安装包、两个进程、两套更新与鉴权**，与「绿色软件」目标相反；本应用已有 IPC 契约检查（206 handler，0 error）来保证前后端一致，再加一层 HTTP 只会增加故障面。
- **后果**：模板生成用「字符串模板 + 类型化数据」而不是 FreeMarker/Jinja2 —— 反正只生成 Java/Python/JMX 文本，模板引擎的语法学习成本 > 收益；且生成物可以用 CodeLab 真编译验证。

### ADR-3：不引入 Faker，扩展现有自研生成器

- **决策**：造数继续用 `src/utils/tdg/` 的 17 类生成器，只补「量级 + 流式落盘 + 去重」。
- **理由**：现有生成器**可校验**（身份证校验位、Luhn、USCC 都算对），Faker 生成的身证号多数过不了校验；多引入一个依赖换更差的正确性，不划算。

### ADR-4：生成物必须可验证，不接受「文件已生成」作为完成标准

- **决策**：所有代码/JMX 生成器都要有 golden-file 单测（固定输入 → 固定输出全文比对），JMX 还要过 `inspectJmx` + 真跑一次；Java/Python 生成物可选走 CodeLab 编译。
- **理由**：生成的代码「看起来对、编不过/跑不对」是这个品类的头号失败模式，而本应用恰好有编译/执行沙箱，不用等于浪费。

## 6. 风险清单与验证口径

### 6.1 三条主要风险

| # | 风险 | 触发形态 | 缓解 |
|---|---|---|---|
| R1 | **生成物「看起来对、跑不通」** | .jmx 能打开但样本数不对；POJO 缺 import；POM 引号转义错 | 生成器全部 golden-file 单测；.jmx 过 `inspectJmx` + 真跑一次对样本数；Java/Python 走 CodeLab 编译 |
| R2 | **静态扫描误报导致功能被弃用** | 把注释里的 `sleep` 报成缺陷；路径拼装导致覆盖率虚低 | 规则可单条开关；命中带行号与原文；明确标注「启发式」；覆盖矩阵三态输出 |
| R3 | **安全越界** | 扫描结果带出明文密码；DB 凭据落明文配置；示例值含真实内网地址 | 扫描结果脱敏、不写日志不导出；凭据只进 vault 加密；示例一律 `example.com`（与 `scripts/check-privacy.js` 同口径） |

### 6.2 每个功能的验收口径（先写死，再实现）

- **生成器类**：固定输入 → 输出与 golden 文件逐字一致；`.jmx` 额外要求真跑一次且 `samples == 线程×循环×接口数`。
- **解析器类**（OpenAPI/Allure/jtl/pom）：用 3 份真实样本（含 1 份畸形/超大）跑通，畸形输入必须给出可读错误而不是崩。
- **扫描类**：先标注已知漏报/误报清单，再用 ≥10 个真实文件抽样人工复核，命中率达标才允许作为发布门禁建议。
- **台账类**：所有统计必须给分母（覆盖 65/100、flaky 3/10 次），禁止只给百分比。
