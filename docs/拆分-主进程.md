## 4. 性能约束

### 4.1 十万级流式写盘（`tdg:`）

| 项 | 写死值 | 依据 |
|---|---|---|
| 每批行数（渲染层决定，主进程只校验） | **建议 2000，硬上限 5000** | `[C-67]`；2000 是「IPC 往返 50 次」与「单批序列化体积」的折中 |
| 单批字节（实测量级） | 10 万行 × 120 B ≈ 12 MB 总量；单批 2000 行 ≈ **240 KB** | 参照 17 类数据平均行宽 |
| 主进程常驻内存增量 | **≤ 单批入参 + 1 MB 缓冲，不持跨批数据**（只持 `fd` + 累计 `rows/bytes`） | ADR-1「元数据全在 vault」的同一约束 |
| 峰值内存（10 万行） | 主进程 **≤ 20 MB**；渲染层 **≤ 单批 + 生成器状态** | 禁止「先攒 10 万行再一次性 join」——那是把流式做成假的 |
| 串行要求 | 渲染层**必须** `await` 上一批 resolve 再发下一批；主进程 handler 内 `writeSync` 同步完成，天然串行 | 并发 append 会打乱行序 = 数据错 |
| 让出事件循环 | 主进程 `write-append` 每次只做一次同步写，无需 `setImmediate`；**渲染层**每批之间 `await setImmediate` 再生成下一批 | 卡 UI 的是渲染层生成，不是落盘 |
| `finish` 的 fsync | 必做，失败不阻塞 rename（与 `electron/main.js:278` 既有做法一致：部分网络盘不支持 fsync） | `[C-65]` |
| 耗时预估（10 万行） | 落盘合计 **0.3–1.5 s**（50 批 × ~240 KB 同步写） | 与 `file:save-text` 的 8 MB 上限同量级 |

[S-107] 明确禁止两种实现：①主进程 `rows.join()` 之前再 `map` 一遍（双份内存）；②`write-append` 里 `fs.appendFileSync`（每批重新 open/close，I/O 放大）。用长开 `fd` + `writeSync`。
[S-108] 字节计数统一用 `tdg-write.js` 的 `textBytes()`（`TextEncoder`），**不要用 `Buffer.byteLength`**（单测在 `types: []` 下会红，`[S-34]`）。

### 4.2 大目录扫描（`scan:`）

| 项 | 写死值 |
|---|---|
| 文件数上限 | 2000（clamp，`[C-53]`） |
| 目录深度 | ≤ 12 |
| 单文件读取 | ≤ 1 MB（`fs.openSync` + 定长缓冲，不用 `readFileSync`） |
| 规则数 × 行数 | 1 MB ≈ 1.2 万行 × 15 条规则 ≈ **18 万次正则/文件** |
| 每文件耗时预估 | 5–20 ms（平均 30 KB）；最坏（1 MB 满读）**40–80 ms** |
| 整次耗时预估 | 2000 个典型文件 **3–8 s**；最坏（2000 × 1 MB）≈ **80 s > 60 s 上限** → 必然走 `truncatedReason: 'timeout'`，所以 60 s 超时不是可选项 |
| 目录遍历本身 | 2000 项 `readdir` 递归 **< 200 ms** |
| 让出频率 | 每 32 文件或 1 MB → `setImmediate`；单次让出 100–300 ms，**取消延迟 ≤ 300 ms 量级** |
| 内存 | 一次只在内存里保留**一个文件**的文本（≤1 MB）+ findings（≤300 × ~300 B）；不做「先收全量文件再扫」 |

[S-109] 遍历必须**一次深度优先、边遍历边扫**，不先 `readdir` 出全量文件列表（全量列表在 10 万文件时会先吃几百 MB 再干活，且 maxFiles 截断要等遍历完才知道）。

### 4.3 Allure 解析（5000 条目）

[S-110] 内存：不保留任何文件的原始 `text`（逐文件读完即丢）；中间态只留 `{ fullName, status }` 轻量数组（5000 × ~200 B ≈ **1 MB**）供 flaky 分组；`cases` 返回 ≤2000。
[S-111] 耗时：5000 文件 × 5 ms ≈ **25 s**，故 30 s 超时是硬需求；每 64 文件让出一次。

### 4.4 `.jtl` 分析（≤256 MB / ≤2,000,000 行）

[S-112] **禁止 `fs.readFileSync(整个 .jtl)`**：256 MB 字符串 + `split(/\n/)` 数组峰值 ≈ **800 MB–1 GB**。落地两条路径：

| 文件大小 | 路径 |
|---|---|
| ≤ 64 MB | `readFileSync(utf8)` → `parseJtlRows(text)`（峰值 ~130 MB） |
| > 64 MB | `createReadStream` 逐块切行：首行 `parseJtlHeader` 取列索引，逐行 `parseJtlRow(line, header)`，原始文本块读完即丢 |

[S-113] 流式路径常驻内存 = 1 MB 读缓冲 + `rows`（2M × 5 字段对象 ≈ **200 MB**，本批唯一的大内存项）。硬边界：文件 > 256 MB 直接拒绝（`[C-72]` 对应行）；行数 > 2M 截断并置 `truncatedReason: 'rows'`。
[S-114] `computeMetrics` 只做 O(n) 单遍 + 一次排序；实现上应把 `elapsed` 抽成 `number[]` 再排序（排对象数组会让峰值翻倍）。

### 4.5 硬不变量（改动必须同步改测试）

1. `covered + missing + undetermined === total`（渲染层 `coverage.ts`，`[C-31]`）
2. `total === passed + failed + broken + skipped`（`allure-parse.js`，`[C-37]`）
3. flaky = `runs ≥ 2 && pass ≥ 1 && fail ≥ 1`（`allure-parse.js`，`[C-38]`）
4. `VAULT_SCHEMA_VERSION === 4` 且 `MIGRATIONS[3]` 是恒等函数（`vaultSchema.test.ts`，`[C-44]`）
