## 0. 总则（适用于本文所有通道与集合）

### 0.1 响应包与取消语义

[C-01] 所有新通道一律返回 `{ success: boolean, data?: T, error?: string, canceled?: true }`。`success: true` 时 `data` 必有（无返回值的通道给 `data: {}`）；`success: false` 时 `error` 必为**可读中文串**，且 `error` 与 `canceled` **不同时出现**。

[C-02] **本项目没有数字错误码**。错误码 = 固定中文文案，前端只允许用「相等」或「包含关键词」匹配（例：`error === '未解锁'`、`error.includes('不是 git 仓库')`）。禁止前端对 `error` 做正则模糊匹配或把它当国际化 key。

[C-03] 对话框类通道用户取消时返回 `{ success: false, canceled: true }`（与既有 `file:pick`、`file:save-text` 一致：`electron/ipc-api.js:116`、`:130`）。UI 收到 `canceled` **不得弹错误提示**，直接静默返回。`canceled` 不算失败、不进错误日志、不写审计。

[C-04] 其余失败（含超时、越界、校验不通过）返回 `{ success: false, error }`，必须让用户看到具体原因（禁止「操作失败」这类笼统文案）。

### 0.2 鉴权与前置

[C-05] 新通道**不做额外的密码校验**：会话解锁是前置条件（未解锁时渲染层不会渲染这些页面），与既有 `jmeter:*`、`jmxlib:*`、`file:*` 一致。

[C-06] **唯一例外**：一切触碰 vault 的读写必须走 `ws:get` / `ws:set`，它们已内置 `未解锁` / `无效的数据类型` / `数据格式错误` / `数据损坏` 四条错误（`electron/ipc-api.js:174-191`）。5 个新集合**不新增任何专用读写通道**。

[C-07] 新域模块必须 `registerXxxIpc(deps)` + 从 `deps` **解构**所需的 main 侧能力（`loadVault` / `saveVault` / `clearCaches` / `getMainWindow` / `appendAudit`…）。裸用这些名字会被 `scripts/check-ipc-contract.js` 的拆分守卫判 error（守卫名单 `scripts/check-ipc-contract.js:87-92`，判定逻辑 `:262-282`），因为拆出去的模块看不到 `main.js` 的模块级状态。

### 0.3 上限与截断通则

[C-08] 所有「数量/体积」上限都是**硬上限**，实现必须 clamp 入参、不得信任渲染层传值（渲染层可以做同样的 clamp 做 UX，但主进程必须再 clamp 一次）。

[C-09] 一切「被截断」的结果必须带 `truncated: true` 并在能给原因时带 `truncatedReason`，取值**只在这 10 个里**：`'findings' | 'files' | 'max-files' | 'depth' | 'file-size' | 'timeout' | 'cases' | 'flaky' | 'rows' | 'labels'`（v10 补 `max-files` 与 `depth`；v12 补 `flaky`，与 `[C-62]` 对齐）。**禁止静默截断**——只给一半数据而不标记，会让用户拿错误结论去做决定。各值语义：`findings`=命中数到顶（`scan:run` ≤300）；`files`=已扫/已读文件数到顶的通用名（`scan:run` 2000、`allure:parse` 5000）；`max-files`=文件数触顶（`scan:run` 的 2000）；`depth`=目录深度触顶（12 层）；`file-size`=单文件超限只读前一部分；`timeout`=整体超时到点返回；`cases`=用例列表被截断；`flaky`=flaky 列表被截断；`rows`/`labels`=行数/标签数被截断。

[C-10] 截断是**确定性的**：同一输入两次调用必须截断在同一位置（排序稳定、遍历顺序稳定）。有并列时必须给二级排序键（例：按 `samples` 降序、同值按 `label` 升序）。

[C-11] 大数组不整块回渲染层：单次 IPC 返回的数组元素数上限写在各自通道表里；超过就截断 + `truncated`（先例：`attachment:list` 只返元数据）。

### 0.4 命名与目录约定

[C-12] 通道名前缀必须是本域的域名词 + `:`，域名词一经确定不得改（改前缀等于断掉契约）。本批固定：`scan:` / `git:` / `allure:` / `tdg:`；扩展域沿用 `jmeter:` / `jmxlib:`（注意 **JMX 脚本库域是 `jmxlib:`，不是 `jmx:`**）。

[C-13] preload 方法名 = 域名词小驼峰 + 通道后半段小驼峰，例：`scan:pick-root` → `scanPickRoot`；`tdg:write-start` → `tdgWriteStart`；`jmxlib:create-batch` → `jmxlibCreateBatch`。

[C-14] 主进程纯函数模块一律 `electron/<module>.js` + 同名 `electron/<module>.d.ts`（让渲染层单测也能 import），单测放 `src/utils/__tests__/<module>.test.ts`——沿用 `jmx-script.js` 的既有模式（`AGENTS.md`「纯函数下沉」）。

### 0.5 只读与安全底线（贯穿 6 个域）

[C-15] `scan:` 与 `git:` 是**只读域**：不写文件、不删文件、不执行任何写命令、不发网络请求。

[C-16] 路径校验三条，缺一条即不通过：

1. **root 包含性**：一切落在用户目录上的路径参数必须校验在「用户本次选择的 root」之下（`path.resolve` 后做前缀比较，拒绝 `..` 与符号链接逃逸）。
2. **越界文案只有一个真源**：越界的错误串不在本条款定义，唯一真源是该域通道表里「路径逃逸 / root 外」那一行（`scan:` 见 §2.2 / `[C-56]`），本条款只引用、**不复制文案**。理由：`[C-02]` 要求前端按字符串相等匹配，同一场景出现两个串必然对不上（2026-11-20 队长裁决 R5 已决）。
3. **唯一豁免：`scan:reveal`**。它的入参保持 `{ file: string, line?: number }`，**不传 `root`、不做 root 包含性校验**。允许的前提是主进程**只做三件事**：① 校验 `file` 是非空字符串且 `fs.existsSync(file)` 为真；② 调 `shell.showItemInFolder(file)`（`line` 只用于 UI 侧提示，不传给系统）；③ 返回 `{}`。**禁止**：读文件内容（不许 `readFile`/`readFileSync`）、解析文件、执行任何命令、把路径写进日志。与既有 `jmxlib:reveal`（`electron/ipc-jmxlib.js:283`，只做 `shell.showItemInFolder`）同口径。

> **为什么豁免 `scan:reveal`**：它的语义是「把这条扫描结果指给人在资源管理器里看一眼」。扫描结果里的 `file` 是相对 root 的路径，落进 `scanRuns` 之后，当初那个 root 可能已经不在了（换盘、换机、用户改了目录）——强制要求 root 会让「打开历史记录再定位」直接失效，而它恰恰是体检功能最有价值的一步。
>
> **风险（照实写）**：渲染层因此有能力让资源管理器**定位到任意一个已存在的路径**。缓解：只做 `showItemInFolder`（不打开、不执行、不读内容），路径必须已存在，攻击面等价于「用户自己的文件管理器」；与既有 `jmxlib:reveal`（`:283`）/ `weekly:reveal`（`electron/ipc-files.js:74`）/ `notes:reveal`（`:260`）完全同构，本批不新增暴露面。

[C-17] 扫描/解析过程中命中的疑似凭据内容（密码、token、连接串）：**不写应用日志、不进审计、不进导出、不落 vault 以外任何文件**（与 `scripts/check-privacy.js` 同口径）。UI 只在本机界面上展示，且页面必须写明「启发式检查，非语法树分析」。

## 1. 数据契约：5 个新集合

### 1.1 通用规则

[C-18] 集合键固定为这 5 个，拼写不得改（**全复数**，2026-11-20 队长裁决 Q3 已决：单数键名改复数）：`pomPages`、`scanRuns`、`coverageRuns`、`caseMaps`、`allureRuns`。加进 `electron/vault-schema.js` 的 `VAULT_COLLECTIONS` 数组**末尾追加**（`electron/vault-schema.js:20-39`，当前 15 项；`entries`/`tags`/`history` 三个基础键不在该数组内，由 `normalizeVault` 单独处理；只追加不插序，减少 diff 冲突）。**键名以本节为准，W1 实现任务的 acceptance 会机械核对这 5 个键**（`VAULT_COLLECTIONS` 含之、`WorkspaceKey` 含之、`vaultSchema.test.ts` 的「每个已知集合都会被补齐成数组」用例含之）。理由：键名写错不会有任何报错——`ws:get` 对未知键走 `无效的数据类型` 分支或返回空数组，`normalizeVault` 直接把未知键丢掉，表现是「页面永远空着」，属静默失效，只能靠机械核对兜住。

[C-19] 同步 `src/types.ts` 的 `WorkspaceKey` 联合类型（`src/types.ts:263-270`），追加 5 个字面量。**`WorkspaceKey` 是 `ws:get`/`ws:set` 的类型闸门**，不同步 = 渲染层调不了。

[C-20] 5 个集合的元素**全部必须有 `id: string`**（非空、集合内唯一）。原因：渲染层统一用 `useCollection<T extends WithId>`（`src/hooks/useCollection.tsx:5-27`），`T` 约束要求 `id`；没有 `id` 的集合无法复用这个 hook，会各自造轮子。

[C-21] `id` 生成规则：`crypto.randomUUID()`（渲染层 `crypto.randomUUID` 可用）；**不得**用自增数字或时间戳（多设备/多窗口会撞）。

[C-22] 时间字段一律 ISO 字符串 `new Date().toISOString()`，字段名固定 `at`（运行时间点）或 `updatedAt`（记录最后修改）。排序、裁剪、比较都用 `Date.parse(at)`。

[C-23] 主进程对集合**只做两件校验**：集合名在 `VAULT_COLLECTIONS` 里、值是数组（`electron/ipc-api.js:182-191` 现状）。**字段级校验在渲染层纯函数里做**（`src/utils/collectionTrim.ts` 的 `trimToCaps` 管上限与裁剪 / 各页面 save 前校验，v10 更正落点），并有单测。理由：给 `ws:set` 加 schema 校验会波及 20 个既有集合，属越界扩张（本批不做，见 §5.3）。

[C-24] 增量上限（**总量**，明文字节 = `JSON.stringify(集合).length` 的 UTF-8 长度）：`pomPages` ≤ 512 KB、`scanRuns` ≤ 1.5 MB、`coverageRuns` ≤ 1.5 MB、`caseMaps` ≤ 1.5 MB、`allureRuns` ≤ 1 MB；**5 个合计 ≤ 4 MB**。理由：vault 是单一加密 JSON，每次落盘全量加解密 + 原子写；4 MB 明文增量对本机（60 条数据 1~4 ms 的现状）仍在可接受量级，超过就是设计错误。**这组数字的唯一真源是代码里的 `COLLECTION_CAPS` 与 `TOTAL_COLLECTION_BYTES`（`src/utils/collectionTrim.ts`，用 `capsOf(key)` 取用）；改上限只改那两个常量并同步本条**（v13 补记，防止契约与常量两套数）。

[C-25] 超上限的处理是**从最旧开始丢**（按 `at`/`updatedAt` 升序丢），不是拒绝保存。丢之前必须在 UI 上给一次提示「历史记录已按上限裁剪，最早 N 条已清理」。裁剪函数必须是纯函数并可单测——**落点是 `src/utils/collectionTrim.ts` 的 `trimToCaps`**（v10 更正：此前写的 `src/utils/runHistory.ts` **从未存在**；现改为 `collectionTrim.ts`，**每个写入点在 `ws:set` 前调用**，返回值里的 `dropped` 数必须对用户可见，对应本条那句「最早 N 条已清理」）。这条由 **W5-B** 落地，见 §4.1 矩阵。

**`trimToCaps` 的签名与返回（v13 对齐实现，2026-11-25——字段名以实现为准）**：

```ts
export function trimToCaps<T>(items: T[], caps: TrimCaps, opts?: TrimOptions<T>): { items: T[]; dropped: number };
```

- **返回的 `items` 指「裁剪后保留下来的条目」**，不是输入条目——**想拿输入请用调用方自己的变量**。注意入参也叫 `items`（那是**输入全量**），同名不同义，是本函数最容易看错的一处：`const cut = trimToCaps(list, caps); cut.items` 是「留下哪些」，`list` 才是「原本有哪些」。
- `items` 是**新数组**（入参数组不被修改），调用方可以放心当副本用。
- `dropped` 是被丢掉的条数；`0` 表示没超限（此时 `items` 与输入等长）。
- 契约此前把返回写成 `{ kept, dropped }`，与实现（`{ items, dropped }`）**字段名不一致**。**裁定：改契约、不改代码**——差异纯属命名偏好，而实现已有一份 + **18 条单测** + 消费者（`src/pages/AssetLedger.tsx` 用 `cut.dropped` / `cut.items`）依赖 `items`，为改名返工三处不划算（v13 修正）。
- 同模块另三个导出**一并点名**（契约此前从未写过）：`capsOf(key)`（按集合键取上限，**未知键回落到保守值**而不是 `undefined`）、`trimNotice(dropped)`（生成上面那句中文提示，`dropped=0` 返回空串——不裁剪就别提示）、`COLLECTION_CAPS` / `TOTAL_COLLECTION_BYTES`（`[C-24]` 那组数字的**唯一真源**：5 个集合的字节上限与 4 MB 合计都从这两个常量来，改上限只改这里）。

**同类字段名扫描（v13，只扫「返回保留集合」这一类）**——口径：把本批 8 个纯函数模块（`git-args` / `tdg-write` / `jmeter-args` / `jmx-script` / `collectionTrim` / `tdg/batch` / `assertions` / `openapi`）里**返回一个「保留/过滤/裁剪后的集合」**的函数逐个取出返回字段名，与契约正文点名处对照：

| 纯函数 | 实现返回的集合字段 | 契约写法 | 结论 |
|---|---|---|---|
| `trimToCaps` | `items` | 原写 `kept` | ❌ **唯一真不一致，本轮已改** |
| `parseStatusZ` / `parseNumstatZ` | `entries` | 未点名（只说「解析」） | ○ 不冲突，本轮已补记（见 `[C-59]`） |
| `mergeDiff` | `files`（+`truncated`） | §2.3 data 写 `files` | ✓ 一致 |
| `parseJtlRows` | `rows`（+`header`） | `[C-71]` 写 `parseJtlRows(text).rows` | ✓ 一致 |
| `filterByScope` | **裸数组**（无字段名） | 「保留哪些条目」 | ✓ 无可冲突的字段名 |
| `listAssertions` / `filterAssertions` | **裸数组** | §3.6 返回 `AssertionSnippet[]` | ✓ 一致 |
| `trimToCaps` 的 `caps` 入参 | `maxItems` / `maxBytes` | 未点名（只给数字） | ○ 不冲突，已由 `capsOf` 收口 |

**结论：除 `trimToCaps.items` 这一处外，「返回保留集合」类字段名与实现一致，残留不一致 0 条。** 扫描命令见 §8 复跑清单（`node -e` 提取各模块 `return {...}` 的键名再与契约比对）。

[C-26] 用户主动删除（单条删除 / 清空历史）必须真的从数组里删除并 `ws:set` 落盘；**不提供「软删除」**（5 个集合都不是审计数据，软删除只会让上限更快撑爆）。

**`scanRuns.skippedSymlinks?` 的口径（v6 修订，2026-11-24，队长裁决）**——把「跳过了多少」从当次返回延伸到历史记录，四条写死：

1. **写入时必填**：每次 `ws:set('scanRuns', …)` 落记录时，新记录必须带上 `skippedSymlinks`（取自 `scan:run` 当次返回的 `ScanRunResult.skippedSymlinks`，`[C-54]`）。它虽然在 TS 类型上是可选（`?`），但**写的时候不许省**。
2. **读取时兼容缺失**：v6 之前落的历史记录没有该字段，历史页渲染必须容错——缺失按 `0` 展示，**不得抛错、不得整页白屏**；同时**不得**把「字段缺失」当作「确认没跳过」来暗示完整性（文案里写「跳过 0 个」只对带字段的记录成立，缺失时显示 `—`）。
3. **历史页展示口径**：历史记录列表的每一条都必须能看出该次扫描的跳过数；`skippedSymlinks > 0` 时**不折叠**，强制展示「已扫 N 个文件，跳过 M 个符号链接」（与 `[C-54]` 当次摘要同一句文案，别在历史页另写一版）。
4. **不需要 bump 版本、也不需要迁移步**：这 5 个集合是本批**新增**的（v3 老库里根本没有这些键），不存在「老数据缺字段要补」的迁移对象；`normalizeVault` 只保证集合是数组、**不校验元素结构**（`electron/vault-schema.js:189-191`），多一个字段少一个字段都原样透传；而本批已经把 `VAULT_SCHEMA_VERSION` 从 3 升到 4（`[C-41]`），这个可选字段**搭这趟车**即可。**不要再 bump 到 5、不要新增迁移步**——「加字段就得动 schemaVersion」是误解，本批已经为 bump 争过一轮，别再制造第二次。

### 1.6 `allureRuns`（5.1 Allure 解析记录）

| 字段 | 类型 | 必填 | 约束 |
|---|---|---|---|
| `id` | string | 必填 | uuid |
| `at` | string | 必填 | ISO |
| `root` | string | 必填 | allure-results 目录 |
| `total` | number | 必填 | |
| `passed` | number | 必填 | |
| `failed` | number | 必填 | |
| `broken` | number | 必填 | |
| `skipped` | number | 必填 | 用例状态计数（`status:'skipped'` 的用例数）——**不是文件数** |
| `retries` | number | 必填 | 判定为重跑的用例数 |
| `skippedFiles?` | number | 可选 | 本次解析被跳过、未参与统计的**文件数**（当次返回见 `[C-63]`）。**写入时必填、读取时兼容缺失**（v6 之前的旧记录没有该字段，缺失按 0 处理且显示 `—`，不得崩）。**与上一行 `skipped` 是两个概念**：一个是文件数、一个是用例状态数，历史页文案不得混用 |
| `clusters` | `{ key:string; count:number; sample:string; samples:string[] }[]` | 必填 | ≤ 50；`key` ≤ 200、`sample` ≤ 500、`samples` **≤ 3 条**且每条 ≤ 500（v12 新增，见 `[C-39]` 的 sample/samples 分工） |
| `flaky` | `{ name:string; runs:number; pass:number; fail:number }[]` | 必填 | ≤ 500；`runs ≥ 2` 且 `pass ≥ 1 && fail ≥ 1` |
| `truncated` | boolean | 必填 | |
| `ms` | number | 可选 | |

[C-37] `allureRuns` 单集合：≤ 20 条；单条 `clusters` ≤ 50、`flaky` ≤ 500；`total === passed+failed+broken+skipped` 必须成立（单测锁死）。

[C-38] **flaky 的定义写死**：同一用例（全名）在**本次解析出的 ≥2 次运行**中既出现过 `passed` 又出现过 `failed`/`broken`。`runs` 是分母，必须显示。单份报告里只有 1 次运行的用例**永远不能**被判为 flaky。跨报告的历史 flaky 归并**本批不做**（见 §5.3）。

[C-39] **聚类键 `key` 的归一（v12 重写，2026-11-25 队长裁决）**——一句话：**`key` 表达模式，不表达实例；诊断信息由 `sample` 承载，不归 `key` 管。**

**抹掉什么（一律抹，不许留）**：

1. **抹掉所有数字**——含**业务数值**（例：`expected discount 15.00 but was 10` 与 `expected discount 20.00 but was 12` 必须归到同一个 key）、含整数/小数/百分比/金额/条数/耗时数字；数字统一替换为占位符（如 `#`），**保留其位置**以维持句式可比。
2. **去堆栈**：`at com.foo.Bar.baz(Bar.java:42)` 这类多行堆栈整段丢弃，只留首行的 message。
3. **去耗时 / 去时间戳**：`took 312ms`、`2026-11-25T12:00:03Z` 一律抹。
4. **去 UUID / 哈希 / 长随机串**：`requestId=9f8e…`、32/40 位哈希整段抹掉。

**为什么这么定（来由写清，别再按「保留业务值才有诊断价值」改回去）**：聚类的目的是**找同一根因**（原始需求：「把报错信息相同的用例聚合在一起……提示『疑似某个前置服务挂了』」）。`expected discount 15.00 but was 10` 与 `expected discount 20.00 but was 12` 极可能是**同一个 bug 的不同数据表现**；按值保留会把它拆成 10 个 `count=1` 的簇，用户看到的是「10 个各出现一次的偶发问题」，而真相是「1 个每单都错的折扣计算」——把同一个 bug 拆散比不聚类更误导。**保留业务值的那个理由是错的**：key 的职责是「同一类」，实例的细节交给 `sample` / `samples`。

**不许抹的例外清单（很重要，否则实现者会把语义数字一起抹掉）**——这些「数字/短记号」本身就是**根因分类依据**，不是易变实例值：

| 必须保留 | 例子 | 为什么不能抹 |
|---|---|---|
| **URL 的主机名与端口号** | `http://api.pay.example.com:8080/v1/charge` → 主机名与 `:8080` 原样留 | 决定「连的是哪个服务」。若两端都把端口抹成同一个占位符，`8080`（支付）与 `9090`（风控）两条本质不同的连接失败会被聚成一簇，正是要避免的误聚 |
| **文件扩展名** | `report.csv` / `report.xlsx` / `report.json` 各自保留扩展名 | 「不支持的文件类型」类报错里，扩展名就是根因分类键；抹掉后三种不同类型的解析失败会被合成一簇 |
| **HTTP 状态码** | `401`、`403`、`500`、`502` 原样保留 | 认证失败与后端崩溃是**完全不同的根因**，`401` 与 `500` 聚到一起毫无意义 |

**边界怎么划**（避免实现时两边都想要）：抹的是**同一条 pattern 下会变化的数字**（金额、耗时、ID、序号）；留的是**换一个值就意味着换一类根因**的记号（服务标识、类型标识、状态码）。拿不准时的判据：**「把它替换掉之后，两条本质不同的报错会不会被合并？」会 → 必须保留。**

**`sample` 与 `samples` 的分工（v12 新增）**：`sample` 是**1 条代表**（该簇里 `count` 最高那条 message 的原文，≤500 字符，给用户一眼看懂这是什么错）；`samples` 是**最多 3 条不同原文的对照**（用于让用户确认「这些确实是同一类不同值」，也用于发现 key 抹过头了——若 3 条 samples 看着不像一回事，说明归一抹多了）。两者都存**未归一的原文**，`key` 才是归一后的串。

同 key 计数 ≥ 2 才进 `clusters`；Top 50 按 `count` 降序、同值按 `key` 升序（`[C-10]`）。

**`allureRuns.skippedFiles?` 的口径（v6 修订，2026-11-24，队长裁决）**——与 §1.3 的 `skippedSymlinks?` 同一套写法，四条同样适用：

1. **写入时必填**：每次落 `allureRuns` 记录必须带上 `skippedFiles`（取自 `allure:parse` 当次返回的 `AllureParseResult.skippedFiles`，`[C-63]`）；TS 类型上是可选（`?`），写的时候不许省。
2. **读取时兼容缺失**：v6 之前的旧记录没有该字段，缺失按 `0` 展示、显示 `—`，不得抛错、不得据此暗示「解析完整」。
3. **历史页展示口径**：每条记录必须能看出这次的跳过文件数；`skippedFiles > 0` 时不折叠，展示「解析 N 个文件，跳过 M 个」。
4. **不得与 `skipped` 混用**：`skipped` 是**用例状态计数**（跑出来 `status:'skipped'` 的用例），`skippedFiles` 是**文件数**。历史页文案必须分别写「跳过 M 条用例」与「跳过 K 个文件」，两个数字不许合并、不许互相顶替、不许共用一个标签（与 `[C-63]` 当次页的文案口径一致）。
5. **不需要 bump 版本、也不需要迁移步**：理由同 §1.3 第 4 条（新增集合 + 元素结构不校验 + 本批 3→4 那次 bump 已覆盖），**不要再 bump 到 5**。

### 1.7 为什么 bump 到 `VAULT_SCHEMA_VERSION = 4`

结论：**bump 到 4**（2026-11-20 队长裁决，Q2 已决）。`VAULT_SCHEMA_VERSION` 由 `3` 改为 `4`（`electron/vault-schema.js:45`），并在 `MIGRATIONS` 里新增 `3: (v) => v` 恒等迁移（`:51-112`）。

[C-40] **bump 不是为了「新应用读旧库」，而是为了「旧应用读新库」。** 前半句本来就成立：`normalizeVault` 对 `VAULT_COLLECTIONS` 里任何一个缺失键都补 `[]`（`electron/vault-schema.js:189-191`），所以旧库被新应用打开时 5 个新集合自动变成空数组，不需要任何迁移步。要解决的问题在反方向——见 `[C-42]`。

[C-41] **v3→v4 没有结构搬移，所以 `MIGRATIONS[3]` 是恒等函数，且必须照队长口径写成 `3: (v) => v`。** 前两步都是既有数据换形状（v1→v2：`history` 数组→按 entryId 归组的对象；v2→v3：`accounts` 并进 `entries`，`:58-111`），这一次 5 个新集合一律从 `[]` 开始，一个既有字节都不动。**这一步的唯一作用是让版本号真的涨到 4**，从而触发 `[C-43]` 的降级保护。迁移步的注释必须原样写明：`v3→v4 只新增集合，结构无搬移；加这一步是为了让降级打开能命中 future 分支`。同时 `migrateVault` 的循环（`:159-165`）会为所有 v3 老库实实在在地调用一次这一步，因此**恒等也要有返回值**（`(v) => v` 返回同一对象；`cur` 已是 `{ ...src }` 的浅拷贝（`:157`），随后写 `cur.schemaVersion = 4`（`:168`）不会污染磁盘上的原对象）。

[C-42] **不 bump 的后果是数据沉默丢失（这就是 Q2 裁决为「改」的原因）。** `normalizeVault` 只在「库里声明的版本 > 当前应用的 `VAULT_SCHEMA_VERSION`」时才保留不认识的字段（`electron/vault-schema.js:192-197`）。不 bump 时两边都是 3，旧版应用读新库：`ver > VAULT_SCHEMA_VERSION` 不成立 → 未知键不被复制（`:193-197` 的循环不执行）→ 它拿着「只有 15 个集合」的对象去 `saveVault`，**5 个新集合就这样被写死成不存在**。表现不是报错，而是「重开应用后元素库/体检记录/覆盖台账/用例映射/Allure 历史全没了」——所以必须堵。注意这是**既有行为**（1.25.0 的 `envProbes`、`tdgDatasets` 同样裸奔），本批只是不再跟着裸奔。

[C-43] **bump 之后的降级安全论证（写进交付说明）。** 库里 `schemaVersion = 4` 时，旧版应用（`VAULT_SCHEMA_VERSION = 3`）读它：`declaredVersion = 4 > 3` → `migrateVault` 直接返回 `{ vault: { ...src }, from: 4, to: 4, applied: [], future: true }`（`:151-155`，**不做任何迁移**，也不把版本号降下来）→ 随后 `normalizeVault` 因为是 `ver > VAULT_SCHEMA_VERSION`，把 5 个集合当作「不认识的字段」原样带上（`:192-197`）→ 旧版保存时它们被原封不动写回去。**结论：降级往返不丢数据。** 代价（照实写）：所有 v3 老库在升级后第一次读库时会走一次恒等迁移（数据零变化）；版本号的语义从「结构变更」扩张到「保后向兼容」，发布说明里必须解释这一句。

[C-44] **W1 必须补的单测（落在既有 `src/utils/__tests__/vaultSchema.test.ts`，该文件已 import `VAULT_SCHEMA_VERSION` / `MIGRATIONS` 同源的 `electron/vault-schema.js`）**，三条断言缺一不可：① `expect(VAULT_SCHEMA_VERSION).toBe(4)`；② `expect(typeof MIGRATIONS[3]).toBe('function')` 且 `migrateVault({ schemaVersion: 3, entries: [] })` 的 `to === 4` 且 `applied` 含 `3`、数据原样（`entries` 不被改）；③ 未知键保留：`normalizeVault({ schemaVersion: 99, caseMaps: [{ id: 'x' }] })` 必须仍然带 `caseMaps`（这条同时锁住 `[C-43]` 的降级论证与 `[C-18]` 的键名）。**同时**保留既有用例「每个已知集合都会被补齐成数组」，它会让 5 个新键漏加 `VAULT_COLLECTIONS` 时直接变红。

### 1.8 类型落点

[C-45] 5 个集合的 TS 类型定义写进 `src/types.ts`，命名固定：`PomPage` / `PomElement` / `ScanRun` / `ScanFinding` / `CoverageRun` / `CoverageItem` / `CaseMapEntry` / `AllureRun` / `AllureCluster` / `AllureFlaky`。**类型文件只有 backend 在 W1 改一次**（见 §4 并行规则），frontend 只 import，不得各自补一份等价 interface。

[C-46] `src/types.ts` 的 `ElectronAPI` 接口里，新方法的入参与 `data` 类型必须与 §2 的通道表逐字对应（`data` 类型名固定为：`ScanRunResult` / `GitDiffResult` / `AllureParseResult` / `JtlAnalyzeResult` / `TdgWriteStartResult` / `JmxBatchResult`…），**禁止用 `any`**（`npm run typecheck` 不拦 `any`，但评审会拦）。

> **命名口径（v4 修订，2026-11-24，队长裁决）**：`jmeter:analyze-jtl` 分析的是 `.jtl` **结果文件**（CSV 形态），不是 `.jmx` **脚本**，所以它的返回类型叫 `JtlAnalyzeResult`——**`Jmx*` 前缀只留给 `jmxlib:` 域（脚本库，例 `JmxBatchResult`）**。两者不共用数据结构，也不许互相复用类型名：混用会让实现者以为 `.jtl` 分析结果和脚本库条目是同一套东西，而它们的字段一个都对不上。

## 2. IPC 契约

### 2.1 通则

[C-47] 4 个新域每个文件只注册自己的通道：`electron/ipc-scan.js`、`electron/ipc-git.js`、`electron/ipc-allure.js`、`electron/ipc-tdg.js`。`electron/main.js` **只加 8 行**（4 行 `require` + 4 行 `registerXxxIpc(...)` 注册调用，2026-11-20 队长裁决 R2 已决），不得在其中写任何业务逻辑（`AGENTS.md`「拆分 setupIpcHandlers」）。

[C-48] 新通道合计 **15 条**：scan 5（`pick-root`/`rules`/`run`/`cancel`/`reveal`）+ git 2（`probe`/`diff`）+ allure 2（`pick-dir`/`parse`）+ tdg 4（`write-start`/`write-append`/`write-finish`/`write-abort`）+ jmeter 1（`analyze-jtl`）+ jmxlib 1（`create-batch`）。`node scripts/check-ipc-contract.js` 的四个数字应从基线 **206 handler / 204 调用 / 224 暴露 / 224 声明** 增长到终值 **221 / 219 / 239 / 239**（四者必须自洽、0 error；数字对不上说明有通道漏接线）。**但不是一步到位**：W1 后是 `219 / 217 / 237 / 237`（只接 13 条），两条扩展通道由**独立补接线任务**各 +1，逐格到达路径见 §2.9 口径三。

[C-49] **四件套同步，缺一即报红**：`electron/ipc-*.js` 注册 → `electron/preload.js` 暴露 → `src/types.ts` 声明 → `npm run check:ipc` 通过。只加 handler 不加 preload 会以 `unused`（warn）出现；只加 preload 不加 handler 是 `调用了未注册的 IPC`（error）；只加 preload 不加类型是 `preload 暴露了但 types 没声明`（warn）——**warn 也必须清零**，否则 TS 侧调不了。

[C-50] 可取消性在这一层只有两种形态，且必须写进通道表：**「否」**（命令级别、毫秒级或只读，靠超时兜底）与**「是」**（长任务，靠 `cancel Token` + 主进程按批 `await` 让出事件循环实现）。**不允许出现第三种**（例如「返回 runId 后靠事件推送」的异步形态）——本批不引入新的推送型通道，`ws:event` 那种模式只在 1.23.0 的长连接场景用。

[C-51] 长任务的「可取消」实现约束：主进程遍历循环里**每处理 32 个文件或每 1 MB 必须 `await` 一次**（`await new Promise(r => setImmediate(r))` 或 `fs.promises`），否则同步 IO 会堵住事件循环，取消消息永远进不来——「界面上有取消按钮但点了没反应」是本批最容易出的假功能。

### 2.2 新域 `scan:`（模块 3 代码体检 + 模块 4.1 覆盖矩阵的取数）

| 通道 | 入参 | data | 性质 | 上限 / 截断 | 可取消 |
|---|---|---|---|---|---|
| `scan:pick-root` | 无 | `{ dir: string }` | dialog，只读 | — | 否（canceled 语义） |
| `scan:rules` | 无 | `{ packs: { id:'audit'\|'coverage'; label:string; rules:{ id:string; severity:string; title:string; desc:string }[] }[] }` | 纯静态，不触盘 | 规则数 = 规则表长度（本批 audit ≤ 30 / coverage ≤ 8） | 否 |
| `scan:run` | `{ root: string 必填, pack: 'audit'\|'coverage' 必填, ruleIds?: string[], maxFiles?: number, token?: string }` | `{ root, pack, files, fileList, bytes, skippedSymlinks, truncated, truncatedReason?, counts, findings, ms }` | **只读** | 单文件 1 MB / 文件数 2000 / findings 300 / 深度 12 / 60 s 超时 | **是**（`scan:cancel` + `token`） |
| `scan:cancel` | `{ token: string }` | `{ canceled: boolean }`（是否真的取消了） | 只置标志位 | — | — |
| `scan:reveal` | `{ file: string, line?: number }` | `{}` | `shell.showItemInFolder`，只读 | — | 否 |

[C-52] `scan:run` 的 `pack` 决定语义：`audit` → 规则命中（findings 按严重度）；`coverage` → **只跑路径抽取规则**，每条命中给 `Finding.key`（抽取到的请求路径原文，未归一化），`counts` 只填 `low`（不代表严重度），真正的三态归一在渲染层 `src/utils/coverage.ts` 做。**同一个通道两个包，不新增 `scan:coverage` 通道**。

**`fileList` 是什么（v10 补记，2026-11-25，按 t33 核对）**：`scan:run` 实际还返回 `fileList: string[]`——本次真正读过的文件的**相对路径**（相对 `root`，POSIX 分隔符，上限与 `files` 同受 2000 限制）。用途是**让 UI 能展示「扫了哪些文件」，而不是只给一个数字**：用户看到 `files: 812` 无从判断「该扫的扫到没有」，配合 `truncated` 与 `skippedSymlinks` 才能判断这次扫描完不完整。约束：①与 `files` 条数一致（`fileList.length === files`，被 2000 上限截断时两者同时截断并置 `truncated`）；②只放路径，**不放文件内容**；③不进 `scanRuns` 落库（历史记录只存计数，避免 vault 膨胀——`[C-24]`），落库字段见 §1.3。

[C-53] `scan:run` 固定上限（主进程 clamp）：`maxFiles` ∈ [1, **2000**]（缺省 **2000**）；单文件读取 ≤ 1 MB（超出只读前 1 MB 并置 `truncated: true` / `truncatedReason: 'file-size'`）；`findings` ≤ 300（`truncatedReason: 'findings'`）；**文件数触顶 2000 → `truncatedReason: 'max-files'`**；**目录深度触顶 12 → `truncatedReason: 'depth'`**（v10 补两个枚举，2026-11-25 按 t32 报备）；整体超时 60 s（到点返回已扫结果 + `truncatedReason: 'timeout'`，**不报错**）。

**两个容易混的字段（v10 写死）**：`files` 是 **number**（真正读过的文件数，用于计数与阈值判断）；**文件清单在 `fileList`**（`string[]`，见 `[C-52]`）。`files === fileList.length` 必须成立，但**语义不同**——别把「总文件上限」这个数字（2000）跟 `fileList` 的条数当两套口径用。

**术语口径（v10 统一，2026-11-25）**：本契约里凡是说「总文件上限 / 文件数上限」，**一律指 scan 的 2000**（本条与 §2.2 通道表同值，别处不得出现另一套数字）。文档里另外三处 `5000` 属于**完全不同的概念**，不要往 scan 上套、也不要顺手改：`allure:parse` 的 `maxFiles ∈ [1, 5000]`（`[C-62]`，读 allure-results 文件个数）、`tdg:write-append` 的单批 ≤ 5000 行（`[C-66]` 附近的 `TDG_LIMITS.maxRowsPerBatch`）、`DataGenerator` 的界面单次生成上限 `MAX_COUNT = 5000`（§6 Q5 已决）。**核对结论：scan 相关的 5000 一处都没有**（v10 全文 grep `5000` 共 12 处，逐处确认均属上述三者）。

[C-54] `scan:run` 遍历时**必须跳过**：`node_modules`、`.git`、`dist`、`release`、`build`、`target`、`.venv`、`vendor`、`out`；后缀白名单：`.java .kt .groovy .py .js .jsx .ts .tsx .xml .yml .yaml .json .properties .txt .md .sql`。白名单外文件不进统计。

**`ScanRunResult.skippedSymlinks`（必填 `number`，v4 修订 2026-11-24，队长裁决）**：本次扫描中**因是符号链接而被跳过的条目数**。推导来源是 `[C-16]` 第 1 条——扫描器不跟随符号链接（跟随就会让 root 包含性校验失效，可能被链到磁盘任意位置），所以每个「本来会进入统计、但因是符号链接而没进」的条目都要计数。**这不是可选装饰**：只给 `files: 812` 时，用户无法判断有没有被静默跳过，而「静默跳过」正是本类工具最先失去信任的地方。UI 必须在扫描结果摘要里展示「已扫 N 个文件，跳过 M 个符号链接」，`skippedSymlinks > 0` 时不得折叠隐藏。它**不并入** `files`（`files` 只数真正读过的文件），也**不计入** `truncated`（截断是另一回事：截断说的是「扫了但有上限」，跳过说的是「压根没扫」）。

[C-55] **`scan:run` 是阻塞式 invoke**（一次调用等到扫描结束才 resolve，**不做** `runId` + 事件推送，2026-11-20 队长裁决 Q1/Q6 已决：扫描有文件数上限与 `truncated`，本就是秒级有界操作，要的是「选错目录能停」的安全阀，不是进度条）。取消机制：渲染层生成 `token`（`crypto.randomUUID()`）→ 需要停时调 `scan:cancel { token }` → 主进程置标志位（靠 `[C-51]` 的按批 `await` 让出事件循环，取消消息才进得来）→ `scan:run` 返回 `{ success: false, canceled: true }`。`scan:cancel` 的幂等语义：token 不存在或已完成 → `{ success: true, data: { canceled: false } }`（不报错）；主进程只维护 `Map<token, { canceled: boolean }>` 并在结束/取消时删除。UI 侧：`canceled` 不算失败、**不弹错误提示、不进错误日志**（`[C-03]`），只把按钮恢复可点。

[C-56] 错误文案（`success:false`）逐条固定：

| 场景 | `error` |
|---|---|
| `root` 缺省/空串 | `未选择目录` |
| `root` 不存在 | `目录不存在` |
| `root` 不是目录 | `不是目录` |
| `pack` 不在枚举内 | `未知规则包：<pack>` |
| `ruleIds` 全部无效 | `规则集为空：<ruleIds 拼接>` |
| 路径逃逸 / root 外 | `路径越界：只允许扫描所选目录内的文件` |
| `scan:reveal` 文件不存在 | `文件不存在：<file>` |
| 其他异常 | 原样 `e.message`（前面加 `扫描失败：`） |

> **这张表是 `scan:` 域错误文案的唯一真源**（`[C-16]` 第 2 条只引用不复制；`[C-02]` 要求前端按相等匹配，别处不得另写第二版）。`scan:reveal` 是唯一不做 root 包含性校验的通道，它的边界与豁免理由见 `[C-16]` 第 3 条。

### 2.3 新域 `git:`（模块 6 影响面取数）

| 通道 | 入参 | data | 性质 | 上限 / 截断 | 可取消 |
|---|---|---|---|---|---|
| `git:probe` | `{ root: string 必填 }` | `{ isRepo: boolean, branch: string, head: string, dirty: boolean }` | 只读 | 超时 10 s | 否 |
| `git:diff` | `{ root: string 必填, scope: 'unstaged'\|'staged'\|'head' 必填 }` | `{ root, scope, files: { path:string; status:string; additions:number; deletions:number }[], truncated: boolean }` | 只读 | 文件数 2000 / 超时 10 s | 否 |

[C-57] **命令白名单只有四条**，参数一律由主进程拼装，渲染层只能传 `root` 与 `scope` 枚举，**任何形如 `args` / `extra` 的入参都不存在**：`rev-parse --abbrev-ref HEAD`、`rev-parse --short HEAD`、`status --porcelain -z`、`diff --numstat -z`（`scope` 只影响后缀：`unstaged` → 无后缀；`staged` → `--cached`；`head` → `HEAD`）。`log` 本批不需要。**命令串拼装与 `-z` 输出解析都必须落在纯函数模块 `electron/git-args.js`**（不塞进 `ipc-git.js`，那里 `require('electron')` 后只能在 Electron 里测；见 `[C-14]`、2026-11-20 裁决 R3/R4）。

[C-58] 子进程固定环境：`GIT_TERMINAL_PROMPT=0`（不弹凭据）、`GIT_OPTIONAL_LOCKS=0`、`cwd = root`、超时 10 s 到点 `child.kill()` 并返回 `命令超时（10 秒）`。**绝不**执行 `commit` / `push` / `checkout` / `stash` / `reset` / `clean` / `config`——不给通道就是最彻底的保护。

[C-59] `git:diff` 的 `additions`/`deletions` 来自 `diff --numstat`，`status` 来自 `status --porcelain` 的两列 `XY`：`??` → `untracked`；`M`/`A`/`D`/`R` 按 `X`（已暂存）与 `Y`（工作区）合成 `staged-modified` / `modified` / `added` / `deleted` / `renamed`。二进制文件 `numstat` 给 `-` 时，`additions`/`deletions` 记 `0` 并在 `status` 后缀 `-binary`。

**`-z` 的分段规则（v11 按 t37 实测改正，2026-11-25——最容易写错的地方，写死）**

> **⚠️ 两条命令的 rename 段序相反**：`status --porcelain -z` **新在前**、`diff --numstat -z` **旧在前**。这是本域一切「改名前后错位」的根源，抄任何一方都要先看清是哪条命令。

1. **`status --porcelain -z`**：每条是 `XY<space>path\0`；**rename / copy 条目多一段，且新路径先出现**——即 `R  <新路径>\0<旧路径>\0`（**新在前**）。解析器必须消费两段，否则后面所有条目整体错位。
2. **`diff --numstat -z`**：每条是 `add\tdel\tpath\0`（`path` 含空格/中文时也不加引号，这正是 `-z` 的本意）；**rename 同样给两段，但旧路径先出现**——即 `add\tdel\t\0<旧路径>\0<新路径>\0`（**旧在前**）。
3. 两条都**必须**用「段号指针」推进（rename 一次消费两段），并各带一条「rename 后面紧跟普通条目」的回归用例：少消费一段时后续条目会整体错位，这条用例会立刻红。段尾空段要跳过。
4. 这三条解析（status / numstat / 段序）**全部由 `electron/git-args.js` 承担**（`parseStatusZ` / `parseNumstatZ`，单测 ≥14 条），`ipc-git.js` 只负责 `spawn` + 超时 + 错误文案。**两者的返回结构（v13 补记）**：`parseStatusZ(text)` 与 `parseNumstatZ(text)` 都返回 `{ ok: true, entries }`（`ok:false` 时带 `error`）——**保留条目在 `entries`**，不叫 `list`/`rows`/`result`；`mergeDiff({ statusEntries, numstatEntries, maxFiles })` 返回 `{ files, truncated }`（`files` 里每条带 `path` / `origPath?` / `status` / `additions` / `deletions`）。

**证据来源与有效期（不要把某版 git 的实测当永久真理）**：上面 `新在前` / `旧在前` 是 **git 2.39.1 的字节实测**，原始输出见 `docs/acceptance/W6-A.md` §3（`status` raw = `M  other.txt\0R  新名字 file.txt\0old name.txt\0`；`numstat` raw = `1\t1\tother.txt\00\t0\t\0old name.txt\0新名字 file.txt\0`）。这是**外部工具行为**，不是我们能锁死的常量：**升级 git 后必须复跑 `src/utils/__tests__/gitArgs.test.ts`**（其中 rename 用例的注释写明了「实测 git 2.39.1」）；若新版 git 改了段序，改契约 + 改用例 + 在交付说明里写明升级前后的差异，不许只改用例不改契约。

**历史修正（描述式，不改写事实）**：本条最初把 `status --porcelain -z` 的 rename 段序写成了「旧路径在前」（与 numstat 相同）。写反的后果**不是报错，而是静默对调**——`path` 与 `origPath` 互换，界面上「改名后 / 改名前」两列内容颠倒，功能看起来完全正常。t37 用真实 git 抓原始字节才发现，据此改正并留下本节。

**`scope` 语义（v11 新增，按 t37 实测补充）**——`status --porcelain` 给的是**整个工作区的视角**，它同时包含索引侧（`X` 列）与工作区侧（`Y` 列）的改动。所以 `scope` **不能只当过滤条件传给 git，必须在解析后再按列过滤**：

| `scope` | 保留哪些条目 | 判断依据 |
|---|---|---|
| `staged` | **索引侧有改动**的（已 `git add`） | `X` 列不是空格、也不是 `?`（即 `X ∉ {' ', '?'}`） |
| `unstaged` | **工作区侧有改动**的 + **未跟踪**的 | `Y` 列不是空格；或 `X=Y='?'`（`??` 未跟踪） |
| `head` | 全量（`HEAD` 与工作区的差异） | 不过滤 |

纯函数 **`filterByScope(entries, scope)`**（`electron/git-args.js` 导出）承担这个过滤，`ipc-git.js` 在 `parseStatusZ` 之后、`mergeDiff` 之前调用它（W6-A 实测位置：`ipc-git.js` 的 `const statusEntries = filterByScope(allStatus, scope)`）。

**不这么做的后果（写清楚，别让人以为可以省）**：不过滤时 `staged` 列表里会混进**只在工作区改动、根本没 add** 的文件——用户看到「已暂存的改动」里躺着一个自己没 add 的文件，会以为已经暂存好并去提交，结果 `git commit` 什么都没带上。这属于「界面说谎」，比少显示几条严重得多。

[C-60] 错误文案：`目录不存在`、`不是 git 仓库`、`git 不可用（未安装或不在 PATH）`、`命令超时（10 秒）`、`未知的 diff 范围：<scope>`、`git 命令失败：<stderr 首行>`。非 git 目录必须给 `不是 git 仓库` 这个**可读中文**，不是把 git 的英文 stderr 直接吐给用户。

### 2.4 新域 `allure:`（模块 5.1）

| 通道 | 入参 | data | 性质 | 上限 / 截断 | 可取消 |
|---|---|---|---|---|---|
| `allure:pick-dir` | 无 | `{ dir: string }` | dialog，只读 | — | 否（canceled 语义） |
| `allure:parse` | `{ dir: string 必填, maxFiles?: number }` | `{ root, total, passed, failed, broken, skipped, retries, skippedFiles, cases, environment, clusters, flaky, truncated, truncatedReason?, ms }` | **只读**（主进程读目录 + 纯函数解析） | 5000 个 result / 单文件 2 MB / cases 2000 / clusters 50 / flaky 500 / 30 s 超时 | 否（超时即截断返回） |

[C-61] 只读三类文件名：`*-result.json`、`*-container.json`（仅用于识别重跑）、`environment.properties` / `environment.xml`（只做 `k=v` 简单解析，**不引 XML 解析器**）。附件（`*-attachment.*`）**不读、不解析、不执行**；HTML 报告不解析。

[C-62] 上限（主进程 clamp）：`maxFiles` ∈ [1, 5000]（缺省 5000）；单文件 ≤ 2 MB（超出的文件跳过并在 `truncated` 里计数）；`cases` 返回 ≤ 2000；`clusters` ≤ 50；`flaky` ≤ 500；整体 30 s 超时（到点返回已解析结果）。

**`allure:parse` 的 `truncatedReason` 只有这 5 个值（v12 补全，2026-11-25）**——此前契约只写了 `cases` / `timeout` 两个，实现按 5 个做的，以本表为准：

| 值 | 触顶的是哪个上限 | 返回时该字段怎么变 |
|---|---|---|
| `file-size` | **单文件** ≤ 2 MB（超出跳过该文件、不解析） | `truncated: true`，被跳过的文件计入 `skippedFiles` |
| `files` | **文件数** `maxFiles` ≤ 5000（只读前 5000 个 result） | `truncated: true`，`cases` 只含已解析部分 |
| `cases` | **用例数** `cases` ≤ 2000（返回给渲染层的 `cases` 被截断） | `truncated: true`；汇总计数（`total`/`passed`/…）仍是**全量**，不是截断后 |
| `flaky` | **flaky 列表** ≤ 500 条（按 `runs` 降序取前 500） | `truncated: true`；`flaky` 只给前 500 |
| `timeout` | **整体** 30 s 超时（到点返回已解析部分） | `truncated: true`，不报错 |

> 取值口径与全局枚举 `[C-09]` 一致（v12 同步在 `[C-09]` 的列表里补上了 `flaky`）。**多值同时触顶时只报一个**：优先级 `timeout` > `files` > `file-size` > `cases` > `flaky`（先发生的先说），其余情况在日志里记，不进 `truncatedReason`（该字段是单值）。

[C-63] 错误文案：`目录不存在`、`不是 allure-results 目录（未找到 *-result.json）`、`读取失败：<文件名>（<msg>）`、`解析失败：<文件名>（<msg>）`。**单文件坏不整体失败**：坏文件计入 `skippedFiles` 并继续，只有「一个可解析的 result 都没有」才返回 `success:false`。

**`AllureParseResult.skippedFiles`（必填 `number`，v4 修订 2026-11-24，队长裁决）**：本次解析中**被跳过、没有参与统计的文件数**，至少包含两类：① 目录里不是 `*-result.json` / `*-container.json` / `environment.*` 的文件（按 `[C-61]` 不读的那一批）；② 本条款说的「坏文件」——读取失败或 JSON 解析失败的 result 文件也计入**同一个**计数，不另开字段（多一个近似含义的计数只会让人不知道该看哪个）。

**不得与 `skipped` 混淆**：`skipped` 是**用例状态**（`status: 'skipped'` 的用例数），`skippedFiles` 是**文件数**；UI 文案必须写清「跳过 N 个文件」vs「跳过 M 条用例」，两个数字不许合并、不许互相顶替。理由同 `[C-54]` 的 `skippedSymlinks`：这是「告诉用户漏了什么」的可观测项，用户看到「812 条结果」时必须能判断有没有被静默跳过。

[C-64] `cases` 元素结构：`{ name:string; fullName:string; status:'passed'|'failed'|'broken'|'skipped'; durationMs:number; retries:number; labels?: string[]; message?: string }`。`name` ≤ 300、`message` ≤ 500（超出截断）。`cases` 按 `status` 降序（failed → broken → skipped → passed）、同状态按 `fullName` 升序（`[C-10]`）。

[C-66] **允许多 writer 并存（v8 修订，2026-11-24，队长裁决：契约向实现让步）**——用 `Map<writerId, WriterState>` 管理，每个 writer 有**独立的文件句柄、独立的累计计数（rows / bytes）与独立的上限判定**，互不干扰。

- **删掉的旧规则**：曾经要求「同一时刻仅一个 writer，且新 start 时自动收掉旧会话」。**这条必须删**：abort 的语义是「取消并删半成品」，拿它给新 start 让路，等于用户没按取消、正在导出的 10 万行数据却没了——**静默掐断用户正在进行的导出属于数据丢失，比多占一个文件句柄严重得多**。
- **并发上限**：同时最多 **8 个** writer。超限时 `write-start` 返回明确错误（见 `[C-69]` 的 `同时写入任务已达上限（8 个）`），**不得 abort 任何已有 writer**——要么让用户先结束，要么自己拒绝。
- **兜底清理**：`app.on('will-quit')` 必须**遍历全部** writer 逐个收尾（删 `.part`），不是只清一个；遍历时单个失败只记日志、不能中断其余 writer 的清理。
- **其余语义不变**：`writerId` 一次性（`finish`/`abort` 之后失效，任何后续调用返回 `写入会话不存在或已结束：<writerId>`）；每个 writer 的行/字节上限仍是 `[C-65]`/`[C-69]` 那套，只是**按 writer 各算各的**。

[C-67] 生成器留在渲染层（TS，`src/utils/tdg/`）：主进程只负责「收一批字符串 → 追加落盘」，**不得在主进程复写一套生成器**（主进程是 CommonJS，不能 import TS；复写必然两套行为漂移）。分批大小由渲染层决定（每批 ≤ 5000），主进程只校验上限。

3. **应用内 spawn jmeter 时 `cwd` 设为 JMX 所在目录**（否则相对路径可能按进程 CWD 解析，行为不确定）。**假设（待确认）**：JMeter 对 `CSV Data Set Config` 的相对文件名默认按「脚本文件所在目录」解析；本应用不以此为唯一保障，而是把 `cwd` 也设过去，靠下面第 4 条的可移植性验收兜住。若实测必须写别的形式（`-J` 参数、绝对路径），按实测结果改契约再改代码。
4. **可移植性验收（可证伪，2.1 的完成标准）**：不是「文件生成了」，而是**把整个脚本库目录整体复制到另一个路径 → 在应用里指向新路径 → 用同一份 `.jmx` 再跑一次 → `samples` 仍等于 线程×循环×接口数 且错误率与原地那次一致**。跑不通就说明相对路径没写对或 CSV 没复制过去。

[C-76] 重名语义（**不幂等**）：目标目录已有同名脚本时按既有 `uniqueName` 规则加 ` (2)` 后缀（`electron/ipc-jmxlib.js:354`），返回实际用了的名字。**禁止覆盖已有脚本**。目录层级沿用既有约束：最多两级（`electron/ipc-jmxlib.js:343-344`）。CSV 副本同理走 `uniqueName`，且 `csv.copied` 必须与 JMX 里写的文件名**逐字一致**（不一致就是「脚本能跑但读错文件」这类最难查的故障）。线程/循环仍必须写成 `${__P(threads,<threads>)}` / `${__P(loops,<loops>)}`（否则 `-J` 覆盖不生效，`samples == 线程×循环×接口数` 必然不成立）；`csvVars[].name` 匹配 `^[A-Za-z_][A-Za-z0-9_]*$`。

[C-77] 错误文案（前三条与既有通道**逐字一致**，不得改）：`还没有设置脚本库目录`、`最多两级：请在根目录或一级目录新建脚本`、`目标目录不存在`；新增：`至少填一个接口`、`接口最多 50 个`、`线程数或循环数超出范围（1–100000）`、`思考时间超出范围（0–60000 ms）`、`CSV 变量名不合法：<name>`、`断言状态码必须是 3 位数字`、`生成的 JMX 未通过结构检查：<error>`、`CSV 文件不存在：<path>`、`CSV 无法解析：<原因>`、`CSV 缺少列：<列名>`、`CSV 没有数据行`、`CSV 太大（> 50 MB）`、`CSV 复制失败：<msg>`。

## 3. 代码生成契约（1.1 / 1.2 / 1.3 / 1.4，零新 IPC）

### 3.1 通用

[C-81] 4 项生成能力**全部是渲染层纯函数**：输入文本/对象 → 输出代码字符串或文件列表。**零新增 IPC**：保存走既有 `file:save-text`（`electron/ipc-api.js:124-136`），元素库走 `ws:get`/`ws:set`。任何「为了生成而新增的 IPC」都算越界（评审直接拒）。

[C-82] 唯一语言是 **Java**。生成器入参保留 `lang?: 'java'` 字段（为了让将来加 Python 不改结构），但本批 `lang` 只接受 `'java'`，传其他值返回 `暂只支持 Java（lang=java）`。**UI 上不得出现 Python/Pydantic/pytest 选项**。

[C-83] 统一返回判别式联合类型（不要抛异常，不要返回 `null`）：
```ts
type GenOk   = { ok: true;  files: GeneratedFile[]; warnings: string[] };
type GenFail = { ok: false; error: string };
type GeneratedFile = { path: string; content: string };  // path 为 POSIX 相对路径
```
`warnings` 用于「生成成功但不完美」的情况（例：`$ref` 循环被截断、字段名被改名、`null` 字段被推断成包装类型），**必须能在 UI 上看到**，不许吞。

[C-84] 生成失败（`ok:false`）时**不落文件、不弹保存框**（方案 §6.4「不产出半成品」）。

[C-85] 生成物不得包含任何非确定性内容：**禁止**时间戳、当前日期、作者/机器名、随机 id、绝对路径。理由：golden 逐字比对必须可复现；含时间戳的生成物每天都会让 golden 变红。

[C-87] **`oasVersion` 与 `version` 是两个概念，不许互相顶替（v9 勘误，2026-11-24）**：`oasVersion` 是**文档规范版本**（`'2.0' | '3.0' | '3.1'`，由顶层 `swagger: "2.0"` 或 `openapi: "3.0.x" / "3.1.x"` 判定）；`version` 是**`info.version`**，spec 作者随手写的业务版本号（可能是 `"1.0.0"`、`"v2"`，甚至空串）。**3.0 与 3.1 只能靠 `oasVersion` 断言**，靠 `version` 断不出来（两份 3.0/3.1 spec 的 `info.version` 完全可能一模一样）；单测与 golden 用例名里也不许用 `version` 表达规范版本。

**为什么是方法不是字段（v9 写明，2026-11-24；任务书里写「字段」是笔误，以本条为准）**：写成 `private final Locator userName = page.locator("#u");` 这种**缓存的 Locator 字段**，读代码的人很容易把它当成「某一刻的元素快照 / 已经取到的元素引用」，页面一跳转、组件一重渲染就以为它还指向原来那个东西——用错的地方极难看出来。写成方法 `public Locator userName() { return page.locator("#u"); }` 每次调用都是一次新的惰性查询，语义与 Playwright 的 Locator 设计一致。**代价照实说**：方法形式多一对括号、类里多几行，可读性优先于这点冗长；Playwright 的 Locator 本身就是惰性查询（构造时不查 DOM），所以「方法返回新 Locator」不带来额外的运行时开销。

### 3.7 golden 文件命名与目录约定

[C-100] 目录固定，**输入与期望输出必须分树**，且**三个 golden 目录名以本条为准**（v9 定死，2026-11-24——不再用 `<generator>` 这种含糊占位，名字必须与实现一致）：
```
src/utils/__tests__/
  __golden__/                         ← 只放「期望输出」
    restassured/<case>.java          单文件输出（generateRestAssured）
    restassured/<case>/<Name>.java + <case>/__manifest.json   多文件输出
    pom/<case>.java（或 <case>/…）    Page Object（generatePageObject）
    pojo/<case>.java（或 <case>/…）   POJO（generatePojo）
  __fixtures__/                       ← 只放「必须真读文件」的输入
    openapi/<case>.in.json|.in.yaml   OpenAPI spec（大文件 / YAML）
    pojo/<case>.in.json               大 JSON 响应体
    allure/<case>/                    allure-results 目录（qa 夹具同树）
```
- **三个目录名写死**：`__golden__/restassured/`、`__golden__/pom/`、`__golden__/pojo/`。**目录名按「产物」起，不按「生成器文件名」起**：`pageobject.ts` 产出的东西叫 Page Object Model，所以目录叫 `pom/` 不叫 `pageobject/`——按文件名起目录反而更难找（找「POM 的 golden」时没人会先想「那个文件叫什么」）。
- **`__golden__/<目录>/` 只允许出现期望输出**（`.java` / `__manifest.json`）；**必须读文件的输入放 `__fixtures__/<载体>/`**（`*.in.json` / `*.in.yaml`）。
- **输入可以内联在测试里（v9 新增，2026-11-24 队长裁决）**：元素表、小型 spec、几行 JSON 直接写在测试文件里读起来最快，**不许为它们建 `__fixtures__` 目录**；只有「必须真读文件」的载体——YAML（需要真解析）、大 spec（几百行贴进测试会淹没断言）、`allure-results` 目录（本身就是一堆文件）——才建目录。理由：**为小样本建一层目录树只会让测试更难读**（跳文件、名字对不上、改一个字段要开两个编辑器）。
- 理由：两棵树的清理与比对策略相反——`__fixtures__` 是喂料（可以和 qa 的 allure 夹具同树、统一清理），`__golden__` 是基准（**只允许人改、不许被 `UPDATE_GOLDEN=1` 之外的任何流程写**）。混在一处时「按目录扫全部输入再跑」与「只比对期望输出」会互相污染。
- **t19 现状**：`pojo` 的 `<case>.in.json` 与 `<case>.java` 当初都落在 `__golden__/pojo/`。W4 做**纯平移**——把 `*.in.json` 移到 `__fixtures__/pojo/`（或按上一条内联进测试），`*.java` 留在 `__golden__/pojo/`，**内容零改动**（不借机重排 golden、不改断言）。
[C-101] `<case>` 命名：全小写 kebab-case，**描述输入特征而不是编号**，例：`oas3-petstore`、`swagger2-ref-loop`、`oas31-nullable`、`json-nested-array`、`json-type-conflict`、`pom-role-locator`、`restassured-escape-quotes`、`pageobject-escape-backslash`。转义 6 类（`[C-86]`）里只有 2 类落成端到端 golden（引号、反斜杠），其余 4 类做单行断言，见 `[C-105]`。

[C-102] 文件写入规范：UTF-8 **无 BOM**、LF 换行、文件末尾**恰好一个**换行、行尾无空格。测试比对前做 `content.replace(/\r\n/g, '\n')` 归一，然后 `toBe` 逐字符相等（不许 `toMatch` 之类的宽松断言）。

[C-103] 多文件输出必须比对 `path` 与 `content` 两样：`__manifest.json` 结构 `[{ "path": "src/test/java/api/BaseTest.java", "file": "BaseTest.java" }]`，`file` 是 golden 目录里的文件名。只比内容不比路径 → 包名/目录写错也全绿。

[C-104] golden 更新方式：测试文件内支持 `UPDATE_GOLDEN=1` 时写入而不是比对（`UPDATE_GOLDEN=1 npx vitest run src/utils/__tests__/<x>.test.ts`）。**CI 与 `npm run test:unit` 默认不设这个变量**；禁止把 golden 更新混进功能提交而不在 PR 说明里列出改了哪几个 golden。

[C-105] 最小 golden 与用例下限：`restassured` ≥ 4 个 golden（含 1 个多文件 + 1 个含 `$ref` 循环告警）；`pojo` ≥ 5 个（含嵌套数组、类型冲突、全 null、`lombok` 开关各 1）；`pageobject` ≥ 3 个（含 role 与 text 定位器）；合计 **≥ 12 个 golden**。转义 6 类（`[C-86]`）**不进 golden**（输出是单行片段）：写在 `src/utils/__tests__/codegenEscape.test.ts` 的内联断言里，≥ 6 条；其中「引号」「反斜杠」两类再各落 1 个端到端 golden（`restassured-escape-quotes`、`pageobject-escape-backslash`，计入上面的 4+3）。

[C-106] Java 生成物的编译验证（可选增强，不阻塞交付）：用既有 CodeLab（`electron/ipc-codelab.js`，本机真 `javac`）编译一次；无 JDK 时**降级为语法自检**并在验收记录里明确标 `未编译验证`——**不得**把「没编译」写成「通过」。golden 比对通过 ≠ 能编译，两者是两道门。

### 3.8 依赖方向

[C-107] 生成器之间只能**单向**依赖：`escape.ts` ← `restassured.ts` / `pojo.ts` / `pageobject.ts`；三个生成器互不引用；`openapi.ts` 不 import 任何 `codegen/*`（它只产出 `ImportedRequest`）。`assertions.ts` 不 import 任何 `codegen/*`。禁止出现循环依赖（`codegen/*` 反向 import `openapi.ts` 即违规）。
