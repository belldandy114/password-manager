## 0. 使用规则（先读，决定后面每条怎么用）

### 0.1 三态判定：只有一种能汇总成「通过」

| 符号 | 含义 | 能否进结论栏 |
|---|---|---|
| ✅ | 命令跑过、退出码符合本文、原始输出贴进报告 | 可以（结论=通过） |
| ❌ | 命令跑过、判据不成立 | 可以（结论=不通过，必须开缺陷） |
| ⚪ | **没跑**（实现未落地 / 环境前置缺失 / 信号拿不到） | **不可以**。只能写「未验证：<具体原因>」 |
| ⚠️ | **部分覆盖**：低层（纯函数 / 单测）已验，端到端那一段没验 | **不可以**。必须写明「覆盖到哪一层 + 缺哪一层」，不许当通过 |

四条硬规则：

1. **拿退出码与计数值说话，不拿截图说话**。布局类判据一律写成「两个数比」，不用「看着不挤」。
2. **不许为了让门变绿而改判据**。本文判据抄自契约；判据与实现不一致时，改实现或走契约修订，不是改断言。
3. **门证据必须对应当前文件版本**。改了文件没重跑对应门 = ⚪，不是 ✅。
4. **⚪ 不算通过**。任何一条 AC 是 ⚪，该需求的完成结论就只能写「未验证」，不得写「通过」。

## 7. 门的执行口径（`ui-geometry` / `ui-detect`）

### 7.1 几何门：Electron 应用只能走「采集 → 离线判定」

`verify-ui-geometry.mjs` 支持 `URL | 本地 HTML | 快照 JSON`；本项目是 Electron，渲染层所有数据来自 `window.electronAPI`（preload 注入）。**把 vite dev 的 URL 交给门是无效采集**：没有 preload → `window.electronAPI` undefined → 登录/主界面进不去，扫到的是登录页而不是设置页/卡片页，🔴=0 属假绿。因此口径固定为：

1. **采集**（S6 新建 `scripts/ui-geometry-snapshot.js`）：`scripts/lib/app.js` 起窗口 → `Emulation.setDeviceMetricsOverride` 固定视口 → 在页面里执行预设 `scripts/lib/ui-probe-core.mjs` 导出的 `collectExpression` → 写 `证据/ui-geometry-<页面>-<视口>.json`；
2. **判定**（离线、可复现）：
   ```
   node <预设>/test-expert/scripts/verify-ui-geometry.mjs 证据/ui-geometry-设置-1280x800.json --viewport 1280x800
   ```
   退出码 0 = 绿；1 = 有 🔴；**3 = ⚪ 未校验（不是通过）**。
3. **必须的采集面**：设置页 7 个 tab 各一屏 × 3 视口（1280/1440/1920）+ 390×844 窄屏 + 卸载弹框打开态 + 网址管理卡片视图（4 张 40 字符卡）。
4. **豁免**：`--waive <豁免表.md|.json>`，输出必须给**三数**：原始 N → 扣除 M → 剩余 R；`R` 不为 0 仍判失败。豁免表每条要有「规则 → 理由 → 谁批的」。

### 7.2 设计门：需要可访问的页面

`verify-ui-detect.mjs` 要 URL / 文件 / 目录，且本机有缓存的 `impeccable` 4.11.0（离线可跑）。两条路：

- **首选**：S6 起一个**渲染层预览桩**（`scripts/ui-standalone-preview.js`：静态服务 `dist/` + 注入 `window.electronAPI` 的 mock，返回固定的 `authIsSetup:true` / `settingsGet` / `entriesList` 等），得到 `http://127.0.0.1:PORT/` 交给设计门扫；
- **兜底**：`--from-json <impeccable 输出.json>` 走判定模式（可在无网机器复现）。

**假绿防线（必须做）**：设计门采集前先断言页面上目标元素真的在（`.set-rail .set-nav` 数 = 7、`.entry-card` ≥ 3、`.modal` 在弹框态 = 1）；这些计数不成立时该次扫描记 **⚪**，不得写「设计门 0 finding = 通过」。

### 10.8 R2 的 A 臂（开启免密 → 重启直接进 Dashboard）：**已复跑通过**（§10.12 为完整证据）

t10 在这里判过 ❌，理由写的是「Electron 37 的 safeStorage 密文跨进程解不开」。**那个结论已被推翻**：失败的两次都不是产品行为，而是**我方 harness 的两个条件错误**——①`scripts/lib/app.js` 的 `launch()` 在没显式传 `userDataDir` 时会**新建一个临时 `--user-data-dir`**，于是每次启动都是新 profile、新 OSCrypt key；②显式固定 profile 的那次用 `taskkill /T /F` 收尾，Local State（存 OSCrypt key 的地方）**没被刷盘**，下一次启动又生成了新 key。

**正确条件下（同一个 `--user-data-dir` + 优雅退出）实测两轮全过**：

```json
// 第 2 次启动时渲染层调 auth:auto-unlock 的原始返回（省略 vault 细节）
{ "success": true, "data": { "unlocked": true, "vault": { "schemaVersion": 5, "entries": [], … } } }
// 同时 auth:auto-unlock-status
{ "success": true, "data": { "enabled": true, "available": true, "updatedAt": "2026-11-27T09:03:51.420Z" } }
// UI：{ "login": 0, "appLayout": true }   ← 没输任何密码就进了主界面
```

**safeStorage 的依赖边界（写进契约/文档，别再踩）**：
1. **同一个 Chromium profile（`app.getPath('userData')` 目录）**——密钥（Local State 里的 `os_crypt.encrypted_key`）是 per-profile 的；换 profile = 换 key = 旧密文必解不开。多开/回归脚本必须复用同一个 `--user-data-dir`，或用默认 profile + 只隔离 `PM_DATA_DIR`。
2. **同一个 OS 用户**——DPAPI 绑定当前 Windows 账号；换用户/换机器解不开（这本就是设计意图）。
3. **profile 必须**真正落盘**——Chromium 在正常退出时才写 Local State；`taskkill /F` 打断会丢掉密钥，下一次启动生成新 key。自动化里要断言这一点：**优雅关闭**（CDP `Browser.close`）后再重启，别用硬杀。
4. 失败时产品行为是对的（自清 + 落登录页 + 不弹窗 + 不阻塞，AC-AU-09 ✅），所以边界一旦不满足，用户看到的是「要重新输密码」而不是崩溃或错误框——这条属于可接受降级。

**顺带核实 main.js:96-108 的注释**：注释写「`--user-data-dir` 影响不到 `app.getPath('userData')`」，**本次实测与之相反**——两次启动的 `USER_DATA_DIR`（应用自己写 `logs/app.log`、`data-location.json` 的那个目录）都落在传入的 `--user-data-dir` 里（见 §10.12 的日志横幅证据）。按实测为准：`--user-data-dir` **确实**会改变 `app.getPath('userData')`。这句话会误导后来人（会让人以为「传了 flag 但日志还在默认目录」），建议 backend 顺手改注释（本轮是验证任务，未改代码）。

**处置建议（需队长/architect 定）**：①确认目标环境（真实用户机、同 userDataDir 稳定）上是否也复现——若只在自动化环境复现，需在验收记录里把 A 臂标「环境限制」而非常绿；②若普遍复现，则启动免密方案要换（例如改用不依赖 OSCrypt 的 OS 级凭据存储，或把密文绑定到稳定的 userDataDir 并显式校验），属**方案级变更**，不是补丁能解决的；③无论哪条，`AC-AU-03` 现在只能是 ❌，且「开启免密的代价提示」必须补一句「凭据失效时会自动清除，需要重新开启」。

## 10.12 t11 复验：R2 A 臂（重启免登录）—— 结论改为 **✅ 通过**

### 10.12.1 三次配置的对照（同一数据目录隔离方式：只改 `PM_DATA_DIR`，不碰 profile）

| 配置 | 两次启动的 profile | 退出方式 | Local State 是否落盘 | `auth:auto-unlock` 返回 | 结论 |
|---|---|---|---|---|---|
| **A** 固定 `--user-data-dir=<U>` | 同一个 `U` | `taskkill /T /F`（硬杀） | **否**（启动 1 结束时 `Local State` 仍不存在） | `{unlocked:false, reasonCode:'decrypt-failed'}` | ❌ 失败 |
| **C** 不传 `--user-data-dir`（走 `launch()` 默认值） | **两次各一个新临时目录**（`pm-ui-ud-QSwd2C` / `pm-ui-ud-Sx2YDe`） | CDP `Browser.close` | 各写各的 | `{unlocked:false, reasonCode:'decrypt-failed'}` | ❌ 失败 |

### 10.12.2 userData 证据（两次启动是同一个 profile）

`app.getPath('userData')` 没有 IPC 通道可取（`preload` 里没有这个暴露面），所以用**应用自己写进 `USER_DATA_DIR` 的两个文件**作等价证明：`electron/main.js:88-92` 是 `const USER_DATA_DIR = app.getPath('userData')` 紧接 `installFileLogging(path.join(USER_DATA_DIR,'logs'))`，所以「`<U>\logs\app.log` 里出现两次启动横幅」= 两次 `app.getPath('userData')` 都等于 `U`。

B 组（`--user-data-dir=C:\Users\…\Temp\pm-t11-udB-eBdRu0`）：
```
启动 1 后： logs\app.log bannerCount=1  lastBanners=["===== 启动 v1.36.0 2026-11-27 17:03:49.762 ====="]
启动 2 后： logs\app.log bannerCount=2  lastBanners=[… 17:03:49.762 …, "===== 启动 v1.36.0 2026-11-27 17:03:53.494 ====="]
两次的 Local State：sha256 前 16 位 = f53b37fd6fcad8f0（启动 2 读到的与启动 1 关闭时写下的**同一个文件**）
```
B2 组同构：横幅 17:04:52.203 / 17:04:55.900，`sha256=057041714ea27e14`。

对照 A 组（硬杀）：启动 1 结束时 `Local State` **不存在**；启动 2 才新建它（`mtime 17:03:32.582`、`sha256 fb1748d4327caf1a`）——**新 profile 的新密钥**，所以旧密文必然解不开。这就是 t10 失败的机理。

> 三组的 `os_crypt.encrypted_key` 解 base64 后的头 8 字符都是 `DPAPI\x01\x00\x00`（Windows DPAPI 包装的 Chromium key），差别在**哪一份** Local State 生效，而不是 DPAPI 本身。

### 10.12.3 上次（t10）为什么失败 —— 一句话

**因为两次启动用的不是同一个 Chromium profile**：一次是 `scripts/lib/app.js` 的 `launch()` 在没显式指定 `userDataDir` 时**自动新建**了临时 `--user-data-dir`（每次启动一个新密钥）；另一次虽固定了 profile，但用 `taskkill /T /F` 硬杀收尾，**Local State 没被刷盘**，下次启动又生成了新密钥。两次都等价于「换了 profile」，与 `electron/ipc-auth.js` 的实现无关。

### 10.12.4 附带核实：`--user-data-dir` 到底改不改 `app.getPath('userData')`

`electron/main.js:96-108` 的注释写「后者只是 Chromium 的开关，影响不到 `app.getPath('userData')`」，**本机实测与该注释相反**：B/B2 两次启动的应用日志都落在传入的 `--user-data-dir` 目录里（`<U>\logs\app.log` 有两条横幅），说明 `USER_DATA_DIR === U`。以实测为准，建议 backend 改掉这句注释（本轮是验证任务，未改代码）。

### 10.14.3 UN-02 锁屏态拦截（安全闸门，真跑）

解锁态先做正向对照，然后 `sessionLock()` 再逐条调三条通道（`removeData:true` 也用正确 `dataDirAck` 试了一次）：

| 调用 | 返回 |
|---|---|
| （对照，解锁态）`appUninstall({removeData:false})` | `{success:true, data:{launched:false, removedData:false, mode:'dev', …}}` |
| `appUninstallInfo()` | `{success:false, code:'locked', error:'请先解锁应用'}` |
| `appUninstall({removeData:false})` | `{success:false, code:'locked', error:'请先解锁应用'}` |
| `appUninstall({removeData:true, dataDirAck:<dataDir>})` | `{success:false, code:'locked', error:'请先解锁应用'}` |
| `appUninstall({removeData:true, dataDirAck:'C:\\Windows'})` | `{success:false, code:'locked'}`（先撞鉴权，没走到 ack 校验） |

**数据目录零删除**（调用前后各做一次递归清单快照）：

```
before: 15 项  attachments/ audit.log background/ backups/ backups/attachments-2026-11-27/
                backups/b1.bak backups/vault-2026-11-27.enc logs/ mine.txt settings.json
                trash.enc.bak update/ vault.enc vault.enc.bak window-state.json
after : 16 项  …（同上）… + settings.json.bak
受管 10 文件：存在性逐项一致（vault.enc / vault.enc.bak / settings.json / audit.log /
              window-state.json / trash.enc.bak 在；trash.enc / autologin.json / clipboard.enc /
              cases.json 本来就没有）；受管 5 目录全部在
```
结论：**before 的每一项都还在，零删除**；唯一新增的 `settings.json.bak` 是应用在锁定时写盘的 `.bak`（`writeFileAtomic` 的产物），删除路径不可能「多出」一个文件。

> 判据修正（写下来免得后来人照抄我的错）：第一版脚本把判据写成「受管文件**全部存在**」，于是 `trash.enc` / `autologin.json` 这类本来不存在的文件把结论误判成 FAIL。正确判据是「**before 的集合仍是 after 的子集**且受管路径存在性逐项一致」—— 「一个都没少」说的是**没有删除**，不是「必须全都在」。
