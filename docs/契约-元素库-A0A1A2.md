## 1. A₀：`PomLocatorKind` 5 → 10（任务书正文曾称 9，已由 `[Z-1]` 追认为 10，来由见 `[A0-1]`）

### [A0-1] 类型与取值清单：**10 个取值**，单一真源在生成器

`PomLocatorKind` 扩为 10 个取值。**接口数量口径**：`PomLocatorKind` 是**一个联合类型**、10 个取值；`KINDS` 是**一份有序清单**（TS）/ **一份字符串数组**（CJS）。三处消费者（生成器 / 试跑 / 点验）**只认这两份清单**，不许各自再写一份 `switch` 白名单。

```ts
// src/utils/codegen/pageobject.ts
export type PomLocatorKind =
  | 'css' | 'xpath' | 'text' | 'role' | 'pw'          // 既有 5 种
  | 'label' | 'placeholder' | 'alttext' | 'title' | 'testid';  // A₀ 新增 5 种

/** 有序清单：顺序 = 界面下拉顺序 = 文档表格顺序，改动必须同步 3 处（本表 / pomModel.ts / element-args.js） */
export const POM_LOCATOR_KINDS: readonly { id: PomLocatorKind; label: string }[];
/** 归一：无 kind / 脏 kind / 空串 / 非字符串 → 'css'（见 [A0-3]） */
export function normalizeLocatorKind(raw: unknown): PomLocatorKind;
```

**勘误 E-1（任务书「5→9」与它自己列的 5 项新增不一致）**：任务书写「扩到 9 种（+`label`/`placeholder`/`alttext`/`title`/`testid`）」，但 5 既有 + 5 新增 = **10**。本契约**以可枚举的新增清单为准取 10**，理由：清单是可逐项验收的、数字不是；若按 9 实现则必然少一种定位方式，而少哪一种都没有依据。**副作用**：所有文档/界面/评审口径统一写「10 种」，写「9 种」的地方按本勘误判为笔误（不是缺陷）。

**E-1 已被队长追认（`[Z-1]`，见 §8），并补上了「9」的来由 —— 下一个读到「10」的人不必再怀疑漏了一种**：

> 参考工程 `1148872017/test-tool` 是 **9 种**，因为它**没有 `pw`**（它不做「原样存一行 Playwright 链」这件事）。本仓库的 9 是「test-tool 的 9」借过来的数，而本仓库在 1.36.0（B6）已经多了一个 `pw`，所以是 **9 + pw = 10**。也就是说：10 = 9（test-tool 口径）+ 1（本仓库既有的 `pw`）；如果将来有人把 `pw` 下线，才回到 9，且那时必须同步删掉 `[A0-6]`③ 与 `[A0-7]`。

### [A0-2] 每种 kind 的**字段契约**（locator 语义 / 是否需要 `roleName` / Java 表达式）

### [A0-3] 老记录 / 脏 kind 的兜底：**一律当 `css`**（三处调用点同一函数）

口径照 `shared/locatorModes.js` 那一套（参考工程 1148872017/test-tool 的定位方式归一：认不出的模式一律降级为最保守的 `css`）——本仓库没有这个文件，因此**口径在这里定死为一条可验收的规则**：

> `normalizeLocatorKind(raw)`：`raw` 是 `POM_LOCATOR_KINDS` 里某个 `id` → 原样返回；**其它一切**（`undefined` / `null` / 空串 / 数字 / 对象 / 未收录的字符串）→ `'css'`。**大小写不敏感、两端空白忽略**（`' CSS '` → `'css'`）。

三个调用点（缺一即不通过）：

| 调用点 | 位置 | 作用 |
|---|---|---|
| ① 生成器 | `src/utils/codegen/pageobject.ts:337`（`switch (el.kind)` 之前） | `const kind = normalizeLocatorKind(el.kind)`；`switch` 落到 `default` 时**仍然**压告警（`pageobject.ts:364` 既有的「未知的元素类型：<k>，已按 css 处理」） |
| ② 渲染层校验/展示 | `src/components/codegen/pomModel.ts:119`（`if (!KINDS.some(...))` 那一行） | 读库投影时先把 `kind` 归一，再进 `validatePage`；即「老库里 `kind` 缺失的元素」在界面上显示为 `css` 且**可保存**，而不是拦「定位器类型无效」 |
| ③ 试跑 / 点验入参 | `electron/element-args.js:328`（`const kind = str(it.kind) \|\| 'css'`） | 已有 `\|\| 'css'`，改成调 `normalizeLocatorKind`（含大小写/空白/未知值），否则 `kind:'CSS'` 会命中 `ERR.badKind` |

**为什么是 `css` 而不是「拦下来」**：老库里的 `kind` 缺失是**历史数据**（1.34.0 及以前的元素没有类型概念时不算罪），拦下来等于「打开老元素就退化到无法保存/无法生成」；而 `css` 是唯一能对任意字符串**都不崩**的解释（`page.locator("<x>")` 最坏是运行期 `not found`，不会生成非法 Java）。代价照实写：老记录里的 `locator` 若其实是文本，会被当 css 而**不命中**——所以面板必须在 `locator` 列旁提示「历史元素类型按 css 处理，请在类型列确认」（`[A0-8]` 文案）。

- **落点**：`src/utils/codegen/pageobject.ts:108-111` 旁（新增 `normalizeLocatorKind`，与 `ariaRoleOf` 同层，同属「输入归一」）；三处调用点见上表行号
- **验收方式**：单测 4 条（`normalizeLocatorKind(undefined)==='css'`、`(' CSS ')==='css'`、`('bogus')==='css'`、`('label')==='label'`）；另 1 条端到端：把 `pomPages` 造数里某个元素的 `kind` 删掉 → 元素表能选中、能保存、`point 生成`不抛

### [A1-2] **唯一入口** `ariaRoleExpr()`：已知 → `AriaRole.<KEY>`；未知 → `page.locator("role=<role>")` 兜底（`[Z-2]`，**不用 `valueOf`**）

**为什么不是 `valueOf`（`[Z-2]` 的三条理由，逐条可验）**：

1. **不是「可能炸」，是「必炸」**：`Enum.valueOf` 对不存在的常量名**固定抛** `IllegalArgumentException`（`java.lang.Enum.valueOf` 的契约）。生成的 Java 能过 `javac`，但跑到那一行 100% 崩；爆炸点在用户第一次跑 POM / 重放阶段，栈里只有 `IllegalArgumentException: No enum constant com.microsoft.playwright.options.AriaRole.FANCYWIDGET`。
2. **两种失败的可观察性不同，兜底文本更好查**：`page.locator("role=<raw>")` 不命中时是 Playwright 的超时 + 截图 + 面板高亮（`[A2-3]` 能直接告诉你「主文档没命中」）；而 `valueOf` 抛异常会把整条用例判红、且不告诉你「其实只是角色名新了一点」。**同样是不工作，一个能定位、一个只能猜。**
3. **与参考工程的做法差异（不照搬）**：`1148872017/test-tool` 用 `AriaRole.valueOf` 是**因为它生成的是 JS**（那边 `AriaRole` 没有编译期枚举契约，`valueOf` 只是一个字符串到常量的查表，查不到也不会因枚举契约throw）；本仓库的产物是 **Java**，`AriaRole` 是**真枚举**，`valueOf` 的失败是运行期异常。**同一个写法在两种语言里代价不同，所以不能照搬。**

**代价照实写**：兜底不保证命中（角色名拼错一个字母就是 0 命中），所以必须有告警（`[A1-3]`），且生成结果的 warning 条数要能被界面看见（既有机制，`generatePageObject` 回 `warnings`）。

- **落点**：`src/utils/codegen/pageobject.ts:438-446`（`role` 分支调用 `ariaRoleExpr`，行为等价）、`:164-175`（`ariaRoleExpr` 本体，**唯一一份**）；`:367-388`（`pwChainToJava` 规则⑥ **也调它**，见 `[A1-4]`）

### [A1-4] `pw` 链规则⑥：**走与 `locatorExpr` 同一个入口**，未知角色**不再整链降级**（`E-4` 改写，v6）

> **v6 改写（review AR-1 → t24 修复后回写）。v5 的原文「保持整链降级」与「链里出现 `role=` 片段即不通过」两条**均已作废**——它们会把 t24 的正确实现判红。** 作废的理由不是「想放宽」，而是原文自身制造了**两套事实**（见下）。

**现状（代码为准，`pageobject.ts:367-388`）**：`pwChainToJava` 的规则⑥ 现在调 `ariaRoleExpr(unquote(roleRaw), warnings)`——**与 `[A1-2]` 的 `locatorExpr` 是同一个函数**：

| 角色 | 规则⑥ 的行为 | 与 `locatorExpr` 的关系 |
|---|---|---|
| 已知（82 项内） | `getByRole(AriaRole.<KEY>{, new Page.GetByRoleOptions().setName("<roleName.trim()>")})` | 逐字相同 |

**为什么必须改（一句话：同一未知角色，两条入口不许给两套事实）**：v5 的口径下，用户把 `fancy-widget` 填成 `kind=role` 得到 `page.locator("role=fancy-widget")` + 一条告警（能跑、不命中、可在面板里看见），而写成 `pw` 链却得到 `ok:false`、「转不出、已用 css 兜底」甚至 `page.locator("body")`——**同一个角色名、同一个用户意图，产出两种完全不同的结果**，用户没法判断该信哪个。t24 因此按 AR-1 收口到同一入口。

### [A2-2] 入参 schema 与校验（错误走 `success:false + error`，不抛）

```ts
// src/types.ts 【新建接口】
export interface ElHitTestInput {
  op?: 'verify' | 'status' | 'stop';   // 缺省 'verify'
  /** 来源一（推荐）：落库元素。主进程自己 loadVault 取真值，保证「验的是库里那一条」 */
  pageId?: string;
  elementId?: string;

  locator?: string;
```

校验顺序（**顺序固定，因为文案是契约**；全部复用 `electron/element-args.js:50-65` 的 `ERR`，不复制字符串）：

| 步 | 条件 | 结果 |
|---|---|---|
| 1 | `op` 不在三值内 | `{success:false, error:'未知的点验操作：<op>'}` |
| 2 | `op==='status'` / `op==='stop'` | 跳过 3-9（这两 op 不需要 url / 定位器，也不读库、**不受解锁闸门约束**——锁定时 `stop` 反而必须能用，见 `[A2-12]`） |
| 3 | 来源恰好一组：`pageId+elementId` 或 `locator+kind`；两组都给或都不给 | `error:'请给出要验的元素：pageId + elementId，或 locator + kind'` |
| 4 | `url` 不匹配 `/^https?:\/\/\S+$/i` | `error: ERR.badUrl`（`请输入 http/https 开头的地址`） |
| 5 | `locator` 空 / >500 | `error: ERR.emptyLocator` / `ERR.longLocator` |
| 6 | `kind` 归一后仍非法 → 按 `[A0-3]` **当 css**，不报错（与 `[A0-3]` 一致；**注意与 `el:trial-run` 的 `ERR.badKind` 口径不同**，见下行） |
| 7 | `kind==='role'` 且 `roleName` 空 / >100 | `error: ERR.roleNeedsName` / `ERR.longRoleName` |
| **8** | **vault 未解锁**（`getPassword()` 拿不到明文）——**任何来源**都拦，不分「落库」与「草稿」 | `error:'密码库未解锁：请先解锁再点验'`（E14，v5 改写） |
| **9** | 来源一（`pageId+elementId`）在库里找不到（**只在已解锁时可达**） | `error:'这条元素在元素库中不存在（可能已被删除）'` |

**v5 重排说明（`[SEC-01]`）**：第 8 / 9 步**换了顺序**（v4 是「9=未解锁、8=元素不存在」）。原因：统一闸门后「未解锁」必然先于「这条元素在不在」，否则会出现「库没解开却报『元素不存在』」的假事实——正是 `[A2-4]` 明令禁止的那类误导。

**第 6 步的口径差异必须写进文档**：`el:trial-run` 对未知 kind 是**拒绝**（`ERR.badKind`，因为它要把 20 条发进子进程脚本，脏 kind 会让脚本报错）；`el:hit-test` 单条、且 `[A0-3]` 规定「脏 kind 当 css」，所以**接受**。两者不一致是**有意的**，理由如上；谁想把它们统一成一种，必须先改 `[A0-3]`。

- **落点**：`【新建】electron/hit-args.js`（`validateHitTestArgs(input)`，纯函数、只 `require('path')` 与 `../electron/element-args` 的 `ERR`，与 `element-args.js:313` 同构）
- **验收方式**：单测 9 条，逐条断言上述文案**全等**（`expect(r).toEqual({ok:false,error:'…'})`）；`grep -c "请给出要验的元素" electron/hit-args.js` = 1（文案只有一处真源）
- **证伪形态**：两组来源都给时「静默取其中一组」（用户以为验的是库里的，实际验的是草稿）；或未知 kind 报 `ERR.badKind` → 不通过

> 2. **`query-failed` 是 `hit-session` 的错误码，不是 `reason`**（`electron/hit-session.js:716`：`closed ? 'cdp-closed' : e.code === 'CDP_TIMEOUT' ? ### [A2-4] 「没连上」不许写成「没命中」（硬口径）

**这是本通道最容易出的假结论**，所以单列一条：`hit`（facts）只在**会话已就绪、查询真的执行过**（`[Z-9]` A 组）时出现。以下情形一律 `success:false + 固定文案`，`data` 里**没有** `hit`：

- 找不到浏览器 / 拉不起 / 没有 `DevToolsActivePort` / 连不上 ws / 没有 page target → `[A2-8]` 的 E1/E2/E3/E4/E5；
- 入参不合法 → `[A2-2]`；
- 整通道超时（`launch`/`attach` 段）→ E16（`点验超时…`），且 `data` 只带 `session`。

> **v3 补记（`[Z-9]` 配套）**：`data` 里**允许**出现 `reason`（取值是 `[Z-9]` 的 **B 组 8–12**：`no-browser` / `launch-failed` / `attach-failed` / `locked` / `element-missing`），形态是 `data: { session, reason }`；**禁止**出现 `found` / `total` / `visible` / `label`——有专门态可渲染，但没有会被误读成「没命中」的字段。入参不合法（`[A2-2]` 那 9 步）**不带** `reason`：那是调用错误，不是会话事实。

> **v5 补记（`[SEC-01]`：解锁闸门扩到全部来源）**：`locked` 这个 B 组值**不再只属于「落库元素」来源**——草稿来源（`locator + kind`）同样会被 `[A2-2]` 第 8 步拦下并回 `locked`。所以面板的状态判断**不许**再按来源分叉（旧写法「草稿不用解锁」已作废），否则会出现「同一个锁定态、两种不同回执」的自相矛盾。

**证伪形态**：面板上出现「0 个命中」而实际原因是浏览器没起来 —— 那就把「没验」说成了「没中」（`[C-92]` / 试跑契约里反复强调的同一条错误）。

- **落点**：`【新建】electron/hit-session.js`（`verify()` 里「就绪前任何失败都 return `{ok:false,error}`，不带 facts」）
- **验收方式**：单测（注入假 `spawn`/假 `fetch`）：让 `DevToolsActivePort` 永不出现 → 断言返回 `{success:false, error:'浏览器起来了但没拿到调试端口（DevToolsActivePort 未生成），请重试'}`、`data.reason === 'launch-failed'`，且**无 `hit` 字段**（`data.found === undefined`）
- **证伪形态**：任一失败分支的返回里带 `hit.found === false` → 不通过

### [A2-5] 单会话单例、`sessionId` 语义、并发

| 项 | 契约 |
|---|---|
| 单例 | 主进程模块级 `let session = null`（**唯一一份**）。`op:'verify'` 时：无会话 → 拉起；有会话且 `url` 相同 → 复用（不重启、不导航）；有会话且 `url` 不同 → `Page.navigate` 后复用 |
| `sessionId` | `crypto.randomUUID()`。语义 = **一次浏览器会话**的标识：跨多次 `verify` **不变**，直到 `stop` / 浏览器自行退出 / 应用退出才换新。**不落 vault**、不进导出；审计里只作分组键（`[A2-13]`）。允许随机的理由：它不参与任何跨机器可比对的产物（`[C-111]` 对 `id` 要求确定性是因为 `id` 进了库、会被 golden 比对） |
| 并发（同参） | 同参 `verify` 叠着来 → **合并到同一个 promise**（第二次调用等第一次的结果），不报 busy。理由：面板「连点两次」是常态，报错等于罚用户手快 |
| 并发（异参） | 不同 `url`/不同 `locator` 叠着来 → `{success:false, error: ERR.busy}`（`正在运行，请稍候`），**不排队**（排队会让悬挂 promise 越积越多，同 `el:trial-run:234` 的取舍） |
| `stop` 幂等 | 同 `sessionId` 的 `stop` 只执行一次；重复调用回 `{stopped:true, alreadyStopped:true}`，不再杀进程 |
| `status` | 只读：回 `session`（无会话时 `{open:false, sessionId:'', port:0, …}`），**绝不拉起浏览器** |

- **落点**：`【新建】electron/hit-session.js`（`let session` / `let inflight` / `startSession()` / `verify()` / `stopSession()`）
- **验收方式**：单测（假 spawn/假 cdp）：连调两次同参 `verify` → `spawn` 只被调用 1 次；异参第二次 → 文案 = `正在运行，请稍候`；`stop` 连点两次 → `kill` 调用计数为 1，第二次回 `alreadyStopped:true`
- **证伪形态**：`status` 把浏览器拉起来了；或两次同参 `verify` 起了两个浏览器进程（用户桌面上会出现两个窗口）→ 不通过

### [A2-6] 超时预算（单段上限不许被调用方突破）

| 段 | 上限 | 说明 |
|---|---|---|
| `launch` | **15000 ms** | `spawn` 浏览器 → 轮询 `<profile>/DevToolsActivePort` 出现（50 ms × 300） |
| `attach` | **10000 ms** | `GET /json/list` → 选 page target → ws 连接 → `Runtime.enable` / `Page.enable` / `DOM.enable` / `Overlay.enable` |
| `query` | **5000 ms** | 一次 `Runtime.callFunctionOn`（计数）+ 一次（取 element）+ `DOM.requestNode` + `Overlay.highlightNode` |
| `total` | **30000 ms** | 整个通道的硬上限；到点返回 E16 并**不杀浏览器**（会话留给下一次 verify 复用） |
| `idleStop` | **600000 ms**（10 min） | 无 `verify` 超过该时长 → 自动 `stopSession()`（`[C-114b]`「最强缓解是缩短会话存在时间」的落地） |

`input.timeoutMs` **只能压小**：`total = min(30000, max(5000, timeoutMs))`，三段各自 `min(单段上限, total)`（与 `element-args.js:292-301` 的 `computeBudget` 同构，**复用同一函数**或同构实现 + 同构单测）。

- **落点**：`【新建】electron/hit-args.js`（`HIT_BUDGET` 常量 + `computeHitBudget(timeoutMs)`）
- **验收方式**：单测 3 条：`computeHitBudget(999999).total === 30000`；`computeHitBudget(100).total === 5000`；`computeHitBudget().launch === 15000`
- **证伪形态**：`timeoutMs: 600000` 能让通道挂 10 分钟 → 不通过

### [A2-7] 只读无副作用：CDP 方法白名单 + 页内**固定脚本**

**允许的 CDP 方法（白名单，多一个即不通过）**：

```
Runtime.enable / Runtime.callFunctionOn / Runtime.releaseObject / Runtime.evaluate（仅 'document' 这一个常量表达式，用来拿 document 的 objectId）
Page.enable / Page.navigate
DOM.enable / DOM.getDocument / DOM.requestNode
Overlay.enable / Overlay.highlightNode / Overlay.hideHighlight
Browser.close（仅 stop 的 L1 降级，且必须用 browser 端点，见 [A2-8]）
```

**禁止**：`Network.*` / `Storage.*` / `Cookie.*` / `DOMStorage.*` / `Debugger.*` / `Input.*` / `Page.captureScreenshot` / `Page.addScriptToEvaluateOnNewDocument` / `Fetch.*` / `Target.*`（除 `/json/list` 这条 HTTP 发现）/ 任何会写页面状态的调用（`DOM.setAttributeValue` / `Runtime.evaluate` 带任意用户字符串）。

**页内脚本只有一段常量**：`HIT_SCRIPT`（模块内一处定义，`electron/hit-args.js` 导出）。`plan`（`{kind, locator, roleName}` 归一后的对象）**只经 `Runtime.callFunctionOn` 的 `arguments` 传值**，**绝不拼进脚本文本**（`el:trial-run` 的 `pwChainPlan` 白名单为什么存在，同一个理由：用户粘进来的 `locator` 是外部材料）。脚本内部**只允许**：DOM 查询、`getClientRects()`、`getComputedStyle`、读 `aria-label` / `title` / `alt` / `placeholder` / `data-testid` / 关联 `label` 的文本（**只回 ≤40 字的 label**）。`HIT_SCRIPT` 全文**不得**出现 `cookie` / `localStorage` / `sessionStorage` / `innerHTML` / `document.body.innerText`。

**点验支持的定位方式（其余一律 `reason:'unsupported'` + 面板文案）**：

| kind | 点验口径 | `approx` |
|---|---|---|
| `css` | `document.querySelectorAll(locator)`（选择器非法 → `unsupported`） | false |

| `placeholder` / `alttext` / `title` / `testid` | 属性精确匹配（`[placeholder="…"]` 等；`testid` = `[data-testid="…"]`） | false |
| `label` | `label` 元素文本匹配 → 取 `control` 或 `for` 指向的控件 | false |

**界面必须写明「点验是近似实现」**：`approx:true` 时面板在结论旁显示 `近似口径（与 Playwright 实现不完全等价）`，且**不得**写「已验证」「等价」这类词（沿用 `[C-120]` / `[C-114b]` 第 4 条对「不许暗示提供更强保证」的口径）。

**白名单的**唯一**落点（`[Z-15]` 修订，v4）**：`CDP_METHODS` 常量定义在 **`electron/cdp.js`**，也就是**唯一发字节的地方**（`send()` 前置校验，越界直接 reject `CDP_FORBIDDEN`，一个字节都不发）。`electron/hit-args.js` **不再持有**第二份白名单——理由与 `[A0-5]` 同一条：**同一份清单放两处，必然漂移**（改一处忘另一处时，`send()` 侧才是真正生效的那份，另一份只会让人误以为已经收口）。

### [Z-8] 「不可见」只在**点验面板内**表达，**不得经 CDP 改写被验页面**

> **v3 新增（队长裁定 `Z-8`）**。`[A2-7]` 的白名单已经把 `CSS.*` / `DOM.setAttributeValue` / 任意 `Runtime.evaluate` 挡在外面，但**没有一句话解释「为什么连改样式也不行」**，实现很容易为了「让用户看见那个不可见的元素」补一个 `CSS.createStyleSheet` 或给 `el.style` 加 outline。所以单列一条。

**规则（三条，缺一即不通过）**：

1. 「命中但不可见」的视觉表达（灰显图标 + `不可见` 标签 + 原因文案 + `approx` 标注）**只在面板自己的 DOM/CSS 里画**：`HitTestPanel.tsx` 的结构 + `redesign.css` **末尾/玻璃段追加**的样式（S3）。
2. **禁止**用 CDP 往被验页面注入/改写样式：`CSS.enable` / `CSS.createStyleSheet` / `CSS.setStyleSheetText` / `DOM.setAttributeValue`（含 `style` 属性）/ `Runtime.evaluate` 改 `el.style` / `Overlay.setInspectMode`（会改 hover 命中行为）**全部在白名单之外**。
3. 高亮仍只走 `Overlay.highlightNode`（浏览器级 overlay：**不改文档、不改计算样式、不进 `document.styleSheets`**，`[A2-7]` 已列）。

**为什么必须这么死（三条理由，写给以后的实现者）**：

- **污染被测环境**：用户可能正拿这个页面手动验业务（同一个 profile 里还有登录态）。点验注入一条 `outline`，用户看到的就不是他要验的那个页面；`z-index` / `transform` 一类的注入甚至会改变可点击区域，直接制造假缺陷。
- **撤不干净**：「注入 → 反问式清理」在真实使用里几乎不会完整执行——面板被关掉、应用崩溃、用户直接切走，清理都不跑；而 `[A2-7]` 的固定脚本是**无状态**的（每调用一次独立查一次），注入式实现一旦泄漏就会长期留在页面上。
- **口径也不对**：「不可见」是**点验结论**，属于面板的事实字段（`visible:false` + `reason:'not-visible'`），不是对被测页面的操作。把它画在页面上等于用「改被测对象」来表达「观察结果」。

**守卫形态（v5 补记，`review-sec` 的「未找到」项；**要求不变，只是把「谁来守」写清**）**：上面第 ① ② 条是**运行时比对**，目前**没有自动化守卫**（代码侧只能证明「我们不写样式」，证不了「页面确实没变」）。所以分两段：

- **(a) 硬约束不变**：规则 1–3 与验收 ① ② ③ **一条都不放宽**。
- **(b) 守卫形态（可接受的证据 + 必须写的限制）**：
  1. **手工证据可接受**：在真机点验后用 CDP 会话手工取 `getComputedStyle` 抽样与 `styleSheets.length` 前后对比，**把两次的原始值贴进交付说明/验收记录**（贴结论不贴数据 = 不算证据）；
  2. **交付说明的「已知限制」必须写一句**：`点验前后页面样式不变：目前无自动化守卫，仅手工抽样验证`；
  3. **将来落地位置（给下一轮，不属本批）**：挂到 `PM_DEBUG` 开关下的冒烟脚本里——`PM_DEBUG=1` 时在 verify 前后各跑一次同一个抽样函数并断言相等（位置提示：与 `docs/agents/testing.md` 的 PM_DEBUG 冒烟脚本同层，**不新增 IPC、不进渲染层**）。

- **落点**：`【新建】src/components/codegen/HitTestPanel.tsx`（不可见态的画法与文案，纯渲染层）；`src/styles/redesign.css`（**末尾/玻璃段追加**，S3）；`【新建】electron/cdp.js`（`CDP_METHODS` 白名单**不含** `CSS.`，`[A2-7]` 收口）；交付说明的「已知限制」小节（本条 (b)-2 那句）
- **验收方式**：① **点验前后对被验页面做样式抽样断言**：点验前取 10 个代表性节点（命中元素、其父、`body`、两个同级、一个 `iframe` 容器等）的 `getComputedStyle` 六项（`color` / `backgroundColor` / `display` / `visibility` / `outlineStyle` / `boxShadow`），点验后再取一次，**两次必须逐项相等**；② 同一页面另断言 `document.styleSheets.length`、`document.documentElement.outerHTML.length`、`document.querySelectorAll('style[data-pm-hit]').length === 0` 前后一致；③ `grep -c "createStyleSheet\|setStyleSheetText\|setAttributeValue\|setInspectMode" electron/hit-*.js electron/cdp.js` → **0**；④ **守卫形态达标**：① ② 的两次原始值已贴进验收记录，**且**交付说明「已知限制」里有 (b)-2 那句原句（可 grep：`无自动化守卫`）
- **证伪形态**：任一样本节点的 `getComputedStyle` 六项在点验前后不一致；或 `document.styleSheets.length` 变了；或页面上出现 `data-pm-hit` 之类的注入标记/样式表；或 `electron/` 下出现 `CSS.createStyleSheet` / `setAttributeValue`；或**交付说明里查不到「无自动化守卫」这句**（把手工抽样冒充自动化守卫）→ 不通过

### [A2-8] 端口与「连谁」：`--remote-debugging-port=0` + `DevToolsActivePort` + **四步发现**

1. 启动参数**只允许** `['--remote-debugging-port=0', '--user-data-dir=<本次 profile 绝对路径>', '--no-first-run', '--no-default-browser-check', '<url>']`。**禁止** `--remote-debugging-address`、禁止 0.0.0.0、**禁止**「先探一个空闲端口再传参」（TOCTOU：并发的另一个进程可能在你探完之后占住它，于是你连的是别人的浏览器）。
2. 等 `<profile>/DevToolsActivePort` 出现，**只取第一行**（端口号）。
3. `GET http://127.0.0.1:<port>/json/list` → 在数组里挑第一个 `type === 'page'`、`url` 不以 `devtools://` 开头、**且 `url` 与本次请求的 `url` 同源**（`scheme + host + port` 三者相等）的 target，取它的 **`webSocketDebuggerUrl`**（`[SEC-03]`）。

**`[SEC-03]` 同源校验（v5 新增，三条硬口径）**：

- **只选同源 page target**。`url` 为空 / 解析失败 / 跨源（scheme、host、port 任一不同）→ **不选**，并按 `[A2-8]` 的既有文案回 `浏览器里没有可点验的页面，请重试`（E5）+ `reason:'attach-failed'`。**不许**「随便挑一个 page 再 `Page.navigate` 过去」——那等于对用户自己已打开的标签注入脚本并导航走，属跨源越界。
- **为什么**：独立 profile 下浏览器里可能已经有用户自己开的页面（同一个 profile 跨会话保留登录态）；「挑第一个 page」在**只有一个标签**时行为正确，在多标签时就可能命中别人的页面——而 `[A2-8]` 第 4 步之后的 `Runtime.callFunctionOn` 是**注入式**操作，落错标签的后果不是「没命中」，是「改了别人的页面」。
- **与既有锁的关系（写死，防实现方被自己的锁卡死）**：`src/utils/__tests__/cdpContract.test.ts` 里有一条「与 `scripts/lib/cdp.js` 逐项相等」的锁（同一条发现链路的真源比对）。**同源校验是 electron 侧新增的加固，不参与逐项相等比对**——比对范围仍然只是「读端口 → `/json/list` → 取 page target 的 `webSocketDebuggerUrl` → 连上才 enable」这四步的**形态**。实现时**不要**为了「让比对通过」把同源校验删掉，也**不要**把它塞进被比对的代码段。
4. 连上**这个 page target** 之后，才允许 `Runtime.enable` / `Page.enable` / `DOM.enable` / `Overlay.enable`。

**为什么不能直连 `DevToolsActivePort` 第二行**：第二行是 **browser 端点**（`/devtools/browser/<id>`），而 `Runtime` / `Page` / `DOM` / `Overlay` 都是 **page target 作用域**的域——在 browser 端点上 `enable` 会被拒（`'Runtime.enable' wasn't found`），现象是「连上了但什么都收不到」。既有真源：`scripts/lib/cdp.js:60`（`/json/list`）、`:84`（按 `type==='page'` 找 target）、`:131`（只认 `target.webSocketDebuggerUrl`）。

**唯一例外（仅 stop）**：`[A2-11]` 的 L1 降级要发 `Browser.close`，它属 **Browser 域**，必须用 browser 端点 —— 允许在 stop 路径用 `ws://127.0.0.1:<port>` + `DevToolsActivePort` 第二行拼出 browser ws，且**只允许发 `Browser.close` 这一条命令**、不 enable 任何域。这是「用对端点」的应用，不是绕过本条的禁令。

- **落点**：`【新建】electron/hit-args.js`（`parseDevToolsPort(text)`：只解析第一行、非数字/0 → `null`；`buildLaunchArgs({exe, profileDir, url})`）；`【新建】electron/cdp.js`（`discoverPageTarget(port)` / `attach(target)` / `send()` / `closeBrowser(port)`）
- **验收方式**：① 单测：`parseDevToolsPort('5778\n/devtools/browser/abc\n')` → `5778`；`parseDevToolsPort('devtools/browser/x')` → `null`；`parseDevToolsPort('0\n...')` → `null`；`buildLaunchArgs()` 的输出里 `--remote-debugging-address` 出现 **0** 次；② 真机：起一次点验后 `netstat -ano | findstr :<port>` **只出现 `127.0.0.1`**；③ `grep -c "/json/list" electron/` 在整个 `electron/` 下 **= 1**（只在 `cdp.js`）
- **证伪形态**：出现 `0.0.0.0` 监听；出现「探空闲端口」的实现（`net.createServer` 试端口）；`electron/` 下出现第二处 `/json/list` 或第二处 `new WebSocket(` → 不通过

### [A2-9] profile：**独立目录**，路径自己算，删除只删自己算出来的

- 目录 = `<DATA_DIR>/el-hit-profile`（`DATA_DIR` 见 `electron/main.js:111` 的 `resolveDataDir()`，`USER_DATA_DIR` 见 `:88`）。**不是**系统临时目录（`[C-114b]` 第 3 条：要继承应用 ACL、仅当前用户可读），**不是** Playwright 的 `.pm-profile`（`element-args.js:43`）。
- **为什么不与 `.pm-profile` 复用一个目录**：① 两个 Chromium 系进程不能同时用一个 user data dir（`SingletonLock` 互斥，后起的直接退出，表现为「点验时 Playwright 试跑窗口被顶掉」）；② `.pm-profile` 的清理语义归 `el:profile-clear`（`ipc-element.js:201-220`），混用会让「清登录态」一次清掉两套。
- **登录态**：hit-test 会话的登录**由用户在被拉起的窗口里自己完成**（与试跑同一条交互），profile 在会话间保留以复用登录态；`stop` **不删** profile。
- **路径包含性校验**：判定函数与 `element-args.js:269-285`（`isInsideProfile`）**同一算法**——`path.resolve` 归一 → `===` 或 `startsWith(base + path.sep)` → `path.relative` 反证不以 `..` 开头。A₂ **把它抽成通用的 `isInsidePath(base, target)` 导出**，`isInsideProfile` 变成它的薄包装（改一处、单测照旧通过）。
- **删除动作的对象永不由调用方给**：`el:hit-test` **不接受** `profileDir` / `pid` / `port` 入参，三者全部由主进程自己算；`stop` 也不接受。谁想把 `profileDir` 做成入参，等于把「任意目录删除」暴露给渲染层。

- **落点**：`electron/element-args.js:269-285`（`isInsideProfile` → 抽出 `isInsidePath` 并导出；`isInsideProfile` 保留为包装）；`【新建】electron/hit-args.js`（`hitProfileDirOf(dataDir)`、`isInsideHitProfile(dataDir, target)`）
- **验收方式**：单测：`isInsidePath('C:\\a\\b','C:\\a\\b')===true`、`isInsidePath('C:\\a\\b','C:\\a\\b-c')===false`、`isInsidePath('C:\\a\\b','C:\\a\\b\\..\\c')===false`；`hitProfileDirOf('C:\\d')==='C:\\d\\el-hit-profile'`；`validateHitTestArgs({profileDir:'C:\\x', …})` 的返回值里**没有** `profileDir` 字段
- **证伪形态**：点验用了用户日常 profile（命令行里出现 `AppData\\Local\\Google\\Chrome\\User Data` 却没有 `el-hit-profile`）；或 `stop` 删了调用方给的路径 → 不通过

### [A2-10] pid 文件 + **双校验才 kill**（禁按进程名批量杀）

- pid 文件：`<profile>/pm-hit.pid`，JSON `{ pid, sessionId, exe, profileDir, startedAt }`，在 `spawn` 成功后**立即**写、`stop` 收尾时删（删不掉不阻塞，写 `app.log`）。
- kill 前**两项都过**才动手：
  1. **进程名** ∈ `{msedge.exe, chrome.exe, chromium.exe}`（大小写不敏感）。取法：`tasklist /FI "PID eq <pid>" /FO CSV /NH`，解析第一列。
  2. **命令行含本次 profile 的绝对路径**，且 `CreationDate ≥ startedAt`（复用 `[C-117]` 第 3 条的口径）。取法：`Get-CimInstance Win32_Process -Filter "ProcessId=<pid>"` 取 `CommandLine` / `CreationDate`（`spawn('pwsh', ['-NoProfile','-Command', …])`，`shell:false`、参数数组）。
- **禁止**：`taskkill /IM chrome.exe`、按镜像名批量杀、`Stop-Process -Name chrome`。那会杀掉用户正在用、带未保存表单的真实浏览器（数据丢失），是本域**后果最重**的一条。
- pid 文件本身是**不可信输入**（手工可改）：所以 pid 从文件读出来后，仍必须走上面两项校验，**不许**「文件里写着 pid 就直接杀」。

> **v6 事实登记（`E-5`，先读代码）：`pwsh → powershell.exe` 回退**——
> **当前实现只调 `pwsh`**（`electron/hit-session.js:258`：`deps.spawnSync('pwsh', ['-NoProfile','-NoLogo','-Command', …])`），**没有** `powershell.exe` 回退（`grep -c 'powershell.exe' electron/hit-session.js` → **0**；仓库里唯一用 `powershell.exe` 的是无关的 `browser-focus.js:45`）。因此：

> 2. 现状后果照实写：只装了 Windows PowerShell 5.1、没装 `pwsh` 的机器上，`verifyProcess` 的**第二项校验拿不到数据 → 按「未过不杀」处理**（表现为 `stop` 降级到 L2/L3 或留痕不杀），**不会误杀**，但也不会优雅关；
> 3. 要落地回退（`pwsh` 失败 → `powershell.exe` 重试一次）**须先改代码再回写本条**；判据固定为「两种 shell 都能起 `Get-CimInstance` 并解出 pid / CommandLine / CreationDate 三个字段」。先写契约后写代码 = 在本仓库里制造「我以为的实现」。

- **落点**：`【新建】electron/hit-session.js`（`writePidFile()` / `verifyProcess(pid, {profileDir, startedAt})` / `killTree(pid)`；进程信息取用 `:255-262` 的 `spawnSync('pwsh', …)`）

### [A2-11] `stop` 三级降级（幂等，失败留痕）

```
L1  CDP Browser.close      （browser 端点，[A2-8] 唯一例外；等 ≤ 2000 ms）
 ↓ 未退
L2  taskkill /PID <pid> /T  （不带 /F，礼貌终止；等 ≤ 2000 ms）
 ↓ 未退
L3  taskkill /PID <pid> /T /F（带 /F；等 ≤ 3000 ms）
 ↓ 仍未退 / 任一步失败
X   放弃端口（session = null，端口不再被本进程引用）+ 写 app.log + 写审计（ok:false）
    → 出参 { stopped:false, killed:true, error:'浏览器没能关掉（已放弃调试端口），请手动关闭那个窗口' }
```

- 每一步都先用 `[A2-10]` 的双校验确认「这个 pid 还是本会话的进程」；**进程名/命令行任一不符 → 立即停手**（说明 pid 已被复用），记审计 `killed:false`。
- `stop` **幂等**：同 `sessionId` 只走一次；L1 成功时把 `killed` 记 `false`（是浏览器自己退的，不是被杀的），只有走 L2/L3 才 `killed:true`。
- **顺序不许调换**：先弃端口还是先杀进程？本条的选择是 **L1→L2→L3 保持端口到 L3 结束**（`Browser.close` 需要端口），只有全部失败才弃端口。理由：先弃端口会让 L1 失去唯一一次「优雅关闭」的机会，而优雅关闭能保住用户在那个浏览器里没提交的表单。

**`[SEC-02]` 审计面的两处补口（v5 新增，8 键口径不变）**：`[A2-13]` 定的 8 键审计里 `stoppedAt` 的语义是「这次会话真的收尾了」。此前有两条收尾路径**根本不写审计**，等于「收尾了却无痕」：

| 路径 | 现状（v4 及以前） | v5 要求 |
|---|---|---|
| `app.on('will-quit')` → `stopSession('quit')` | 只杀进程 / 删 pid 文件，**不写审计** | **必须写**一条 `{ action:'el-hit-session', sessionId, browserId, host, startedAt, stoppedAt, hits, killed, ok }`（`ok` 按实际收尾结果），`reason`（quit）**不进审计**——8 键之外不加字段 |
| `startSession` **失败**（拉不起 / 拿不到端口 / 连不上） | 只有 `data.reason` + 日志，**不写审计** | **必须写**一条：`stoppedAt` = 失败时刻、`killed:false`、`hits:0`、`ok:false`；**host 仍只记 `URL.host`**（拿不到 URL 时记空串，不许把整条 URL 塞进去） |

**为什么不能靠日志兜**：审计是**可查询**的（`audit:list`），日志会截断到 4000 行、且不能按字段查；「启动失败无痕」在排障时最容易被误读成「用户没点过」。这与 `[C-119]` 第 7 款对「清理失败无痕」的处理同一条思路。

- **落点**：`【新建】electron/hit-session.js`（`stopSession(reason)`：`'user' | 'quit' | 'lock' | 'idle'`；`startSession` 的三个失败出口共用同一个 `auditHitSession(ok:false)`）
- **验收方式**：真机 3 次正常 stop + 1 次强杀（`stop` 前先手工结束浏览器主进程，模拟 L3 路径）：每次 `stop` 返回后 3 秒内查 `tasklist | findstr chrome` 无本 profile 进程、`netstat` 无该端口；幂等：连点两次第二次回 `alreadyStopped:true` 且 `tasklist` 调用计数不增加（单测）
- **证伪形态**：`stop` 后仍有本 profile 的孤儿进程；或 `stop` 超时阻塞界面 > 8 s（三级加起来的上限 7 s，超了就是没设超时）→ 不通过

### [SEC-01] `el:hit-test` **统一要求解锁**（收紧，不采用「只加审计 + 限速」）

> **v5 新增（队长裁定 `SEC-01`，来自安全评审 `review-sec`）。** v4 的解锁闸门只覆盖**落库来源**（`pageId + elementId`），草稿来源（`locator + kind`）在**锁定态**即可拉起浏览器。裁决：**收紧到全部来源**。

**三条理由（逐条写清，别再被"只加审计"的方案说服）**：

1. **元素库本身是 vault 数据**：锁定态下不该由库（或其编辑态）驱动任何**联网动作**——连「打开一个页面」都算。闸门放在「来源」上而不是「能力」上，本身就是错的。
2. **`label` + `text` 合起来等价于「锁定态下的内网页面文本读取器」**：返回体 `label` 是页面可见文本（≤ 40 字），而 `kind='text'` 的判定是 `indexOf` **子串成员**判定（`[A2-7]` 的近似口径）——于是「逐字猜文本、看命中与否」就是一个**布尔 oracle**：攻击者能在锁定态下用几十次 verify 把内网页面里的字读出来。**只加审计与限速不消除能力，只是留痕**（留痕对已发生的数据外带没有补救作用）。
3. **「草稿来源可绕开」这个前提本来就不成立**：走草稿来源（`locator + kind`）的唯一自然场景是「用户正在元素库里编辑一个还没保存的元素」，而**编辑元素库必须解锁**。所以要求解锁**不损失任何正常路径**，只掐掉了一条被构造出来的旁路。

**改动的四处（必须同时一致，任何一处漏改都会出现两种回执）**：

| # | 位置 | v4（作废） | v5（现状） |

| 1 | `[A2-2]` 校验顺序 | 第 9 步 = 来源一未解锁；第 8 步 = 元素不存在 | **第 8 步 = 任何来源未解锁**；第 9 步 = 元素不存在（只在已解锁时可达） |
| 2 | `[A2-4]` 出参说明 | `locked` 只属落库来源 | v5 补记：**`locked` 对所有来源成立**，面板不许按来源分叉 |

| 4 | `[Z-16]` 责任表 | 未提及解锁面 | 新增一行「解锁闸门覆盖全部来源 = **S1 单测已覆盖（离线）**；锁定态真机未验（t15 路径③）」 |

**受影响的既有断言（预期改值，不许删 `it`）**：`src/utils/__tests__/hitArgs.test.ts:240` 与 `hitSession.test.ts:223` 里断言旧文案/旧来源分叉的两条，随实现改成「任何来源 + 新文案」后**必然变红**——这是**预期改值**：改断言内容可以，**删掉 `it` 不行**（删了就等于把这条安全闸门的守卫一起删了）。

- **落点**：`【新建】electron/hit-args.js`（第 8 步前置到元素存在性判定之前；E14 文案改一处）；`electron/hit-session.js`（`verify()` 入口先判解锁，两来源同一条路径）；`src/components/codegen/hitPanelModel.ts` / `HitTestPanel.tsx`（`locked` 态不再按来源分支）；`src/utils/__tests__/hitArgs.test.ts:240`、`hitSession.test.ts:223`（改断言、留 `it`）
- **验收方式**：① 单测：锁定态 + `locator+kind` → `{success:false, data:{session, reason:'locked'}}`，**且 `spawn` 调用计数 = 0**（这条最关键：闸门必须在起浏览器**之前**）；② 单测：锁定态 + `pageId+elementId` → 同一文案同一 reason；③ 单测：已解锁但元素不存在 → `element-missing`（证明第 8/9 步顺序真的换了）；④ `grep -c "或用 locator + kind 点验草稿元素" src/ electron/` → **0**（旧文案清零）

### [SEC-03] `pickPageTarget` **同源校验**（且不参与「与 `scripts/lib/cdp.js` 逐项相等」的比对）

> **v5 新增（队长裁定 `SEC-03`，安全评审建议本轮内修）。** 详见 `[A2-8]` 第 3 步下方那段硬口径。这里只登记裁定与「锁的边界」两句。

- **规则**：只允许选与目标 URL **同源**（`scheme + host + port` 三者相等）的 page target；拿不到 `url` 或跨源 → 按 E5 `浏览器里没有可点验的页面，请重试` + `reason:'attach-failed'` 处理，**不许**「挑一个再 `Page.navigate` 过去」。
