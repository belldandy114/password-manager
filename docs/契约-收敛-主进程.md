## 0. 通用规程（四批共用，先看这一节）

### 0.1 「四件套」与 `check:ipc` 的判定矩阵

`scripts/check-ipc-contract.js` 只做**静态文本对齐**，判四件事（`check()`，`:284-312`）：

| # | 判定 | 代码位置 | 级别 |
|---|---|---|---|
| ① | `ipcMain.handle/on('x:y')` 注册了，但 `preload.js` 没有 `invoke/send('x:y')` | `:294` `unused` | **warn** |
| ② | `preload.js` 有 `invoke('x:y')`，但主进程没注册同名 handler | `:297` `missing` | **error** |
| ③ | `preload.js` 暴露了方法名，但 `src/types.ts` 的 `ElectronAPI` 没声明 | `:300` `untyped` | **warn** |
| ④ | `types.ts` 声明了方法，但 `preload.js` 没暴露 | `:303` `unimplemented` | **error** |

**这张表决定了删除顺序**。只有 ② 和 ④ 会让门变红，且两者的成因分别是「handler 先死」和「types 先死」：

- ④ **unimplemented（error）**：先删 `preload` 而 `types` 还留着 → 立刻红。
- ② **missing（error）**：先删 handler（含删 `ipc-*.js` 文件）而 `preload` 还 invoke → 立刻红。
- ①（warn）：先删 `preload` 而 handler 还注册 → 只 warn。
- ③（warn）：先删 `types` 而 `preload` 还暴露 → 只 warn。

### 0.2 硬性删除顺序（**四批一律照此，不许并行**）

```
S1 渲染层消费方（页面 / 组件 / 纯函数 / 其单测）      → tsc 红也没关系，先摘调用
S2 types.ts：方法声明 + 该域的结果类型                → check:ipc 只 warn(③)
S3 preload.js：暴露方法 + ipcRenderer.invoke           → check:ipc 只 warn(①)
S4 main.js：require 行 + register 调用 + 域内状态/定义  → 主进程已不引用该域
S5 删 electron/<域>.js + .d.ts + 其单测                → 全仓 grep 0 命中
```

**为什么是这个顺序（不是反过来）**：S2–S4 期间每一步都只落在 warn 侧，门始终是绿的；反过来（先删文件）会同时制造 ② missing 与启动期 `MODULE_NOT_FOUND`，两种红混在一起，分不清是漏删还是漏接。

**先摘调用、后摘定义**（方案 §3.2 的原话）在主进程里等价于 **S4 必须早于 S5**：`main.js` 的 `require`/`register` 调用是「调用」，`ipc-*.js` 文件里的 `ipcMain.handle` 与纯函数模块是「定义」。调用点先摘，定义后摘，任何中间态都能 `node --check` 通过且能启动。

```
6  spawn(which('node'), [scriptPath], { cwd: workDir, shell:false, windowsHide:true, stdio:['ignore','pipe','pipe'], env 见 4.4 })
7  读 stdout 的哨兵行 @@EL_TRIAL@@{json}；整次 20 s 定时器到 → taskkill /PID <pid> /T /F（复用 ipc-codelab.js:181 的做法）
8  finally：删临时 .mjs（删失败只记 console，不抛）
9  回结果：解析成功 → { success:true, data:{results, ms} }；解析失败 → { success:false, error:'试跑脚本输出无法解析' }
```

**为什么不复用 `ipc-codelab.js` 的 `runStep`**：它把子进程输出拆行推给渲染层（`:45-54`），且 `MAX_OUTPUT_LINES=2000` 会截断；试跑要的是**一条结构化 JSON**，走推流反而要再加一层拼装。**但必须复用它的三个做法**：`shell:false`、`windowsHide:true`、超时用 `taskkill /PID /T /F` 杀**进程树**（`:181`；Playwright 会拉起 chrome + 它的子进程，只杀 node 会留孤儿 —— 这正是方案验收第 5 条「跑完 3 s 内无残留 node 进程」要卡的点）。

### 4.4 两盏灯的判定口径（**不许照抄代码调试的写法**）

| 灯 | 判定 | **必须避免的错误写法** |
|---|---|---|
| `node` | `which('node')`（`electron/which.js`）返回非空 | ❌ **不能用 `process.execPath`**。`ipc-codelab.js:33` 的 `nodePath = process.execPath` 注释就写着「Electron 自带 Node」——那是给「用 Electron 当 Node 跑用户代码」的场景判绿的；试跑要的是**真 node**（Playwright 要 `node_modules` 解析 + 真进程树），拿 `electron.exe` 冒充会让用户在「没装 Node」的机器上看到绿灯然后必然失败 |
| `playwright` | 在 `workDir` 下跑 `node -e "require.resolve('playwright')"`，退出码 0 即亮 | ❌ 不能只看 `node_modules/playwright` 目录存在；`require.resolve` 才是「这个目录下真的能 require」 |

**关键环境变量**：spawn 时必须**删掉** `ELECTRON_RUN_AS_NODE`（`ipc-codelab.js:129` 给子进程**设成 `'1'`**，那是它自己的用法；试跑继承它会让真实 node 行为异常）。`env` 基线：`{...process.env, ELECTRON_RUN_AS_NODE: undefined}`（delete 而非置空串）。

**缺灯行为**（§12.6 原文）：**固定文案 + 禁用按钮，不静默失败**。三组文案互不混淆：

| 场景 | 文案 |
|---|---|
| 没配工作目录 | `先指定 Playwright 工作目录` |
| node 缺失 | `未找到 node（试跑需要 Node ≥ 22）` |
| playwright 包缺失 | `工作目录里没有 playwright 包（需要 node_modules/playwright）` |

### 4.5 并发保护（语义照录制器的「已有会话在录制」）

- 模块级单变量：`let running = null;`（`{ runId, child, scriptPath }`），与 `ipc-codelab.js:30` 的 `current` 同型。
- 第二次调用 → `{ success:false, error:'正在运行，请稍候' }`，**不排队、不静默复用**（§12.7 原文：「不静默排队」）。
- 并发粒度是**全局**而不是 per-dir：profile 目录同一时刻只能被一个进程用（§12.7 表格第 3 行），全局锁顺带把这个约束也保住了。
- `finally` 里必须 `running = null`，且**异常路径也要清**（否则一次崩溃后按钮永久禁用）。
- **不做**「超时自动重试」：重试会掩盖真实失败，与「失败要回 Playwright 原文」冲突。

### 4.6 profile 目录与清空

| 项 | 决定 | 依据/理由 |
|---|---|---|
| 位置 | `<工作目录>/.pm-profile/` | §12.6「其下 `.pm-profile/` 作为持久 profile」 |
| 生命周期 | **保留**，不随跑完删 | §12.6 第 6 步「profile 目录保留（登录态要在）」 |

- 页面存在 `input[type=password]`
→ 输出 `{ needLogin: true, results: [] }`，主进程回 `data.needLogin = true`，**`success` 仍为 `true`**（这是「跑通了但需要人」而不是「调用失败」），UI 文案「页面需要登录：请在弹出的窗口里登录后点『重试』」。

### 4.7 临时 `.mjs` 的落点与清理（对 §12.2 原文的一处收紧）

**方案原文**：在 Playwright 工作目录写一个随机名临时 `.mjs`。
**本文收紧为**：`<工作目录>/.pm-trial/trial-<ts>-<rand6>.mjs`（固定子目录）。三个理由，都能被证伪：

1. **node 模块解析仍成立**：Node 从脚本所在目录向上找 `node_modules`，`.pm-trial/` 的上一级就是工作目录，`require('playwright')` 照常命中。**证伪方式**：在工作目录放一个 `console.log(require.resolve('playwright'))` 试跑，能打出来就说明解析没坏。
2. **不污染用户工程根**：用户的工作目录就是他自己的项目根，往根上扔 `.mjs` 会被他的 git / lint / `tsconfig` 扫到。
3. **清理面收敛**：启动时扫 `.pm-trial/` 里超过 1 天（按 `mtime`）的 `*.mjs` 一次删掉——**这条是新增的残留兜底**，因为 `finally` 删不掉的情况真实存在（应用被强杀、磁盘占用、文件被占用）。**清理范围写死为这一层、非递归**，不做「按模糊匹配删工作目录里的东西」。

**收尾断言**（方案验收第 5 条）：跑完 3 s 内 `.pm-trial/*.mjs` 数量回到跑前值、无残留 `node.exe` 子进程（`tasklist` 里该 runId 的 pid 及其子进程都没了）、`.pm-profile/` 仍存在。

### 5.3 清理（先导出成功 → 二次确认 → 只清 4 个）

| 约束 | 写死口径 | 理由/断言 |
|---|---|---|
| 前置 | 本次会话**必须已有一次成功导出**（内存标志位，不清零到退出） | 方案 §11.7 原文「必须先导出成功」；标志位不做持久化（重启后要求重新导出，属保守一侧） |
| 二次确认 | 确认框必须写明「将清空 4 个集合、共 N 条；`pomPages` 与代码体检历史**不受影响**；`caseMaps` 清空后『改了代码该跑哪些用例』在本应用内彻底没有了」 | 最后一句来自方案 §11.8-3，属**已知不可逆后果**，必须在确认框里出现，不能只在文档里 |
| 清理方式 | 逐集合 `ws:set(key, [])` ×4（**不新增批量通道**） | `ipc-api.js:194-203` 已有；`value` 必须 `Array.isArray` |
| 写盘代价 | 4 次 `ws:set` = 4 次 `saveVault`（每次全量序列化 + AES-GCM 加密 + 原子写） | 属已知成本；清空后库变小，第 2–4 次更快。**不许**为了省 3 次写盘去改 `ws:set` 或加批量通道（那会动到「新增 IPC 必须走 loadVault/saveVault」的既有约定与四元组） |
| 顺序 | 固定 `uiRecordings → allureRuns → coverageRuns → caseMaps`（**最"贵"的最后**：中途失败时用户已确认要删的集合按此顺序递减） | 可重入：失败后再点一次，已空的集合再置空是幂等的 |
| 部分失败 | 返回 `{ ok:false, done:[...], failed:{key,error} }`，界面必须逐个列出「已清 X，未清 Y」 | 禁止「静默整体成功」或「静默整体失败」 |
| 永不清 | `pomPages`（有 UI：代码生成 → 元素库）、`scanRuns`（有 UI：代码工具 → 代码体检），以及其余全部集合 | 方案 §11.7 原文 |
| 清完不得做的事 | 不 bump `schemaVersion`、不写迁移、不删集合键 | 删入口不删数据；回滚只需 `git revert` |

### 5.4 验收（可判定）

1. 导出 → 打开 JSON → 4 个键齐全、`schemaVersion===5`、`exportedAt` 可解析；条数与 `ws:get` 逐集合相等。
2. 取消保存框 → 清理按钮**仍禁用**（导出失败不放行）。
3. 清理后 `ws:get` 4 个集合 `length===0`；`pomPages` / `scanRuns` 条数**与清理前逐条相等**（不是「看起来还在」）。
4. 关掉应用重开 → 4 个集合仍为 0，`pomPages` / `scanRuns` 仍在。
5. 整库备份体积在清理后**下降**（可观测旁证；不设阈值，因为压缩率随内容变）。
6. 清理**不产生**新 IPC：`check:ipc` 的四元组在 B8 只应因 `el:*` 四条 +4。
