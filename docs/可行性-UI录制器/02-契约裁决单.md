### 2.3 为什么必须改判（三条硬理由，都可复核）

1. **不落库就交付不了「产物三选」**：`.mjs` 与 `*.spec.ts` 要逐步骤的动作序列，`pomPages` 只有元素（`pomModel.ts:18-33`）。用户已拍板三产物一次做全 → 步骤必须落库。
2. **`:325` 的两条理由在新场景下都不成立**：①「新增集合不用 bump」——对「新版读旧库」成立，对「**旧版读新库**」不成立，而 C-40 明确说 bump 解决的是后者；②「元素结构不校验」——`normalizeVault` 确实不校验元素字段（`electron/vault-schema.js:200+`），但这恰恰意味着**丢了就是丢了，不会被任何断言发现**。
3. **代价不对称**：不 bump 的代价是「降级一次 → 录制记录静默消失」（`vault-schema.js:192-197` 的代码路径，不是推测）；bump 的代价是「一条禁令需要豁免 + 5 条断言改写」。前者是数据丢失，后者是治理成本。**这就是改判的全部理由，不含任何「顺便升级」的动机。**

### 2.4 `MIGRATIONS[4]` 的幂等要求与验收方式

**要求（写进契约 `[C-111]`）**：`MIGRATIONS[4]` 只做两件事——①缺失的 `uiRecordings` 补成 `[]`；②`pomPages[].elements[]` 中**缺 `id` 的元素回填一个 `id`**。**已含 `id` 的元素必须保留原值**，重复执行结果不变。

**回填的 `id` 必须可复现（本裁决新增的技术取舍）**：回填路径**不用** `crypto.randomUUID()`（`[C-21]` 是给**新建元素**定的），改用确定性派生——由 `(pageId, elementIndex, name, locator)` 经 `crypto.createHash('sha1')` 派生 32 位十六进制并拼成 uuid 形状。理由三条：

1. **可逐字比对**：AC-8 要求「重开应用后 `uiRecordings` 与 `pomPages` 逐字段相等」，随机 id 会让同一份 v4 老库在两台机器上迁移出两个不同结果，golden 与回归都没法比；
2. **迁移可重跑**：确定性派生在「人为重放迁移」时结果稳定，便于排障；
3. **引用完整性**：`UiStep.elementId` 与 `PomElement.id` 的对应关系一旦随机，跨机器导出/导入的录制会指错元素。

**验收方式（幂等，三条判据，全部可跑）**：

```text
判据 1（幂等·有 id 不改写）：对 { schemaVersion: 4, pomPages: [{ id:'p1', elements:[{ name:'a', locator:'#a', kind:'css', id:'fixed-id' }] }] }
        跑 MIGRATIONS[4] → 元素 id 仍 === 'fixed-id'
判据 2（幂等·重跑恒等）：对上一步的输出再跑一次 MIGRATIONS[4] → JSON.stringify 前后严格相等
判据 3（回填·可复现）：对同一份「无 id」老库在两处独立调用 MIGRATIONS[4] → 两次产物严格相等（不允许依赖随机源/时间）
```

**证伪形态**：任一判据返回不等 → 判失败；回填用 `randomUUID` 使判据 3 出现差异 → 判失败（不是「偶发」）。

### 2.6 回滚论证（方向必须写对）

**写成契约原话**：**bump 后降级不丢数据（`[C-43]`），不 bump 才丢（`[C-42]`）。**

- **bump 后**：库里 `schemaVersion = 5`，旧版应用（`VAULT_SCHEMA_VERSION = 4`）读它 → `declareVersion = 5 > 4` → `migrateVault` 直接走 future 分支返回、**不做任何迁移也不降版本号**（`electron/vault-schema.js:171-175`）→ `normalizeVault` 因 `ver > VAULT_SCHEMA_VERSION` 把 `uiRecordings` 当「不认识的字段」原样带上（`:192-197`）→ 旧版保存时原封不动写回。**结论：降级往返不丢数据。**
- **不 bump**：两边都是 4，`ver > VAULT_SCHEMA_VERSION` 不成立 → `:192-197` 的保留循环不执行 → 旧版应用拿着「只有 5 个新集合」的对象去 `saveVault` → `uiRecordings` **被写死成不存在**。表现不是报错，而是「重开应用后录制记录全没了」。
- **上游报告此处说反过**（`可行性分析报告-UI录制器.md` E-02 已勘误）：原报告写了「降级版会把新集合丢掉」并由此推出「降级前必须备份」这条误导性前置。**本裁决按 C-42/C-43 的代码事实改写，不沿用原报告表述。**

| **后果（含代价）** | **代价**：①生成的脚本**不能开箱即跑**——使用者必须先导出环境变量（`ACCOUNT` / `PASSWORD`），交付说明与脚本头部注释都要写这一句；②`valueRef` 的命名由用户填（界面给默认建议值），写错就是运行期空值，需要在生成时做「未填 `valueRef` 的 fill 步骤」告警（`warnings`，`[C-83]` 口径）；③录制「填了什么都看不见」，用户可能误以为没录上——界面必须在步骤行显示 `已隐藏（N 位）`。**收益**：口令**从不离开页面**（页内只数长度）、**从不进日志**（零 console）、**从不进生成物**（只有占位）、**从不进 vault**（只有 `{length}`）。 |

## 6. 待确认项的收口结果（**2 条均已由队长裁定，见 `06-队长裁定.md`**）

**U-1｜`[C-24]` 的「合计 = 单集合上限之和」在追加第 6 个集合后不再成立 → 已裁定：B 案 7.5 MB。**

- 议题：`[C-24]` 写「5 个集合合计 ≤ 6 MB」，等式 = `512 + 1536×3 + 1024 = 6144 KB`；追加 `uiRecordings`（1536 KB）后 Σ = **7680 KB = 7.5 MB ≠ 6 MB**。
- **裁定（J-1）：选 B，总量改 7.5 MB**，`uiRecordings ≤ 1.5 MB` 并入 `[C-24]` 正文清单；`[C-24]` 正文 + `TOTAL_COLLECTION_BYTES` + 那条既有单测**三处同改**。
- **为什么 A（维持 6 MB）不成立**：`src/utils/__tests__/collectionTrim.test.ts:195-199` 有**一条当前是绿的**硬断言「`Σ COLLECTION_CAPS.maxBytes === TOTAL_COLLECTION_BYTES`」；S1 一登记 `uiRecordings`，Σ 就变 7680 KB。A 案要成立只能删这条断言，而 `[C-113]` 明令「不许删既有 `it`」——所以 A 在本仓**不是保守，是制造一条假绿**。B 的运行时影响面为 0：该常量只作 `capsOf()` 的未知键兜底，无跨集合求和校验。
- **契约落点**：`[C-24]` 正文（已改「6 个合计 ≤ 7.5 MB」）、`[C-24a]`（已改「已裁定 B」）、新增 `[C-24-note]`（声明 v15 历史理由段自 v17 起以 `[C-24]` 为准）。**代码侧**（`collectionTrim.ts` 常量 + `collectionTrim.test.ts:195-203` 的 `it` 标题与 `toBe` 值）归 **S1 数据模型分片**，本任务不改代码。

**U-2｜「5 invoke」的第五条是哪条 → 已裁定：`record:status`（5 invoke + 1 推送，四元组 226/224/245/245）。**
