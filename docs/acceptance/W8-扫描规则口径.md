## 0. 结论先行

| 问题 | 结论 |
|---|---|
| findings 上限提到多少？ | **明细上限 300 → 2000**，**仓库落库上限仍保留 300**（两个常量拆开，别再用一个数管两件事） |

### 1.3 顺带查出来的一处口径错误（不是设计取舍，是 bug）

```
electron/ipc-scan.js:194-198
  if (perFileSuppressed > 0) {
    suppressed += perFileSuppressed;
    if (!truncatedReason) markTruncated('findings');   // ← 折叠被写成了「findings 截断」
    else truncated = true;
  }
```

后果链：`truncated=true` + `truncatedReason='findings'` → `AuditTab.tsx:113` 的 notice 与 `:271` 的横幅
都会说「**本次扫描结果被截断（findings），命中数可能偏少**」——而实际上**一条明细都没丢**，只是同一文件
同一规则的第 4 条起被折叠（折叠数量 `suppressed` 已如实回传，`:289-297` 另有说明）。
W7 那次 `findings=300`（真到顶）与 `suppressed=1034`（只有折叠）**同时成立**，所以两种原因在界面上完全分不开。

修法（写进方案 B）：折叠用契约 C-09 已允许的 **`'suppressed'`**，`truncated` 与「明细被砍」解耦。
另建议把 `markTruncated` 的「先到先得」（`:133`）改成**按优先级取一个**，照 `electron/allure-parse.js:177`
`pickReason` 的做法：`timeout > max-files > depth > file-size > suppressed > findings`。
现状下「先遇到折叠」会把后来的 `timeout` 盖掉，用户看到的原因可能是错的。

## 2. 建议方案

### 2.1 两个方案摆在一起

| | 方案 A：只提高硬上限 | 方案 B：上限 + 总数统计保底（**推荐**） |
|---|---|---|
| 后端行为 | `MAX_FINDINGS = 1000`，到顶仍 `break` | 明细到 2000 后**继续遍历**，只累加 `totalFindings` / `counts`，不再 push finding、不算 snippet |
| 总数 | 到顶后**仍然不可知** | **永远可知**（`totalFindings` 必返回） |
| UI 能说的话 | 「已展示 2000 条（达到上限，实际可能更多）」 | 「命中 5,231 条，明细展示前 2,000 条」 |
| 改动量 | 小（改常量 + 文案） | 中（返回字段加 1 个、`:200` 改成计数分支、UI 文案分流） |
| 「本次扫描结果被截断」 | 只要到顶就还得说（因为真不知道总数） | 只在**扫描覆盖**被砍时才说 |
| 风险 | 用户仍拿不到「到底多少问题」；下次还想再提上限 | 到顶后仍要跑完全部文件 → **耗时不降**，但 60 s 超时 + 2000 文件上限已经兜住（实测 702 文件 466 ms，20 条规则 795 ms） |

**为什么 B 的成本可接受**：到顶后省掉的只是 `findings.push` 与 snippet 截取，**规则匹配本来就要跑**
（不然 `suppressed` 也算不出来）。实测 704 文件全量匹配 795 ms，离 60 s 超时还有 75 倍余量。

### 2.2 为什么是 2000（三条成本口径）

**(a) IPC 序列化体积**（实测 203 B/条，Electron structured clone）：

| 明细上限 | 序列化体积 | 判断 |
|---|---|---|
| 300 | 59 KB | 现状，完全无压力 |
| **2000** | **396 KB** | 可接受（一次 `invoke` 的量级，远低于 vault 单集合 1536 KB） |
| 5000 | 989 KB | 接近落库上限，且 `maxFiles=2000` 下**收集不到这么多**，纯浪费 |

**(b) 渲染层表格成本**（`FindingsTable.tsx:33-68`，**没有虚拟化**，7 列全量渲染）：

- 300 行 = 2,100 个 `<td>`；2000 行 = **14,000 个**。`maxHeight: 460` 的滚动容器里 DOM 全在。
- 结论：**2000 必须配分页或虚拟化**（建议每页 200 行，或默认按「规则 × 文件」折叠 + 展开）。
  若本轮不想动表格，则上限取 **1000**，并把「表格虚拟化」单独立项。
- ⚠️ 本任务**没有实测** 2000 行的渲染耗时（只出口径、不跑 UI）。验收判据见 §2.3 第 5 条。

**(c) 落库体积**（`src/utils/collectionTrim.ts:188`，`scanRuns ≤ 20 条 / 1536 KB`）：

- 2000 × 203 B ≈ **396 KB/条** → 20 条里只能留 **3 条**就开始从最旧丢（`trimToCaps` 的字节分支）。
- 所以：**展示上限 ≠ 落库上限**。建议 `scanRuns[].findings` 保留 **300**（C-29 原口径不变，vault 体积零增长），
  当前会话展示用 2000；历史里那条记录照样带 `totalFindings`，历史页显示「命中 5,231 条（历史只留前 300 条明细）」。

**(d) 真实大仓库规模**：本仓库 704 文件 → 收集 589 条（0.84 条/文件）。
`maxFiles=2000` 是硬边界 → 同密度下最多 ≈ **1,670 条**。**2000 正好覆盖「扫满 2000 个文件」的最坏情况**，
再高没有意义（除非同时提 `maxFiles`）。若目标仓库是 Java + Selenium 套件（命中密度明显更高，实测本仓库
`ui-*` 类就占 335/589），2000 也会到顶——但那时 `totalFindings` 会给出真数，用户不必再猜。

### 2.3 落地形态（实现方按这个改，别自创）

1. **拆常量**（三个数各管一件事）：
   ```js
   // electron/ipc-scan.js
   const MAX_FINDINGS_DETAIL = 2000;  // 收集明细的上限（原 MAX_FINDINGS）
   // 渲染层 src/components/codeaudit/scanModel.ts
   export const FINDINGS_CAP = 2000;          // 当前会话明细上限（沿用旧名，减少调用点改动）
   export const SCAN_HISTORY_FINDINGS_CAP = 300; // 落库上限（C-29 不变）
   ```
2. **后端到顶后改为计数**（`ipc-scan.js:199-213`）：
   ```js
   for (const h of hits) {
     if (counting) { totalFindings += 1; if (counts[h.severity] != null) counts[h.severity] += 1; continue; }
     if (findings.length >= MAX_FINDINGS_DETAIL) { counting = true; totalFindings = findings.length; markTruncated('findings'); }
     ... push ...
   }
   ```
   `counting` 一旦为真，**不 `stop`、不 `break` 外层遍历**（这正是现在 `:200` 的问题）。
3. **返回字段**（`scan:run` data 加 1 个必填字段，`src/types.ts:1018` 同步）：
   ```ts
   totalFindings: number;   // 命中总数；未到顶时 === findings.length
   ```
   `counts` / `suppressed` 语义不变。**不要**用 `findings.length + suppressed` 反推总数——两条口径会打架。
4. **`truncatedReason` 语义收窄**（契约 C-09:40 / C-53:399 同步）：
   - `findings` = **明细列表到顶，总数已知**（不再是「总数不可知」）；
   - 折叠 → `suppressed`（修 §1.3）；
   - 其余 4 个（`timeout` / `max-files` / `depth` / `file-size`）保持「扫描覆盖被砍」。
5. **渲染层**（`AuditTab.tsx`）：
   - `:88` 落库改用 `SCAN_HISTORY_FINDINGS_CAP`；
   - `:158` `hitCap` 改成 `truncatedReason === 'findings'`（别再靠 `findings.length >= CAP` 猜）；
   - `:117-119` toast、`:245` panel meta、`:271-286` 横幅、`:113` notice 按 §2.4 分流；
   - 表格分页/虚拟化：每页 200 行，判据「2000 行时首屏可交互 < 300 ms」（用 `PerformanceObserver` 或
     `requestAnimationFrame` 前后打点，参照 `scripts/ui-glass-opaque-scan.js` 的帧时间口径）。

### 2.4 「本次扫描结果被截断」 —— 什么时候才该出现

**一句话判据**：只有当「**还有文件没扫 / 没扫全**」时，命中数才可能偏少；只有这时才能说这句。

| 情形 | `truncatedReason` | 该说的话（口径） | 「本次扫描结果被截断…」 |
|---|---|---|---|
| 明细到顶、总数已知 | `findings` | 「命中 **{totalFindings}** 条，明细展示前 **{cap}** 条（同一文件同一规则最多 3 条）」 | ❌ **不许出现** |
| 同文件同规则折叠 | `suppressed`（新） | 「另有 **{suppressed}** 条同类命中已折叠，不是没扫到」 | ❌ 不许 |
| 整体超时 | `timeout` | 「扫描超时（60 s），只扫了 {files} 个文件，命中数可能偏少」 | ✅ 出现 |
| 文件数触顶 | `max-files` | 「只扫了前 2000 个文件，命中数可能偏少」 | ✅ 出现 |
| 深度触顶 | `depth` | 「目录超过 12 层未深入，命中数可能偏少」 | ✅ 出现 |
| 单文件超限 | `file-size` | 「{n} 个文件只读了前 1 MB，命中数可能偏少」 | ✅ 出现 |

对应代码判据（`AuditTab.tsx:271` 现在是一刀切 `data.truncated &&`，必须改成）：

```ts
const coverageCut = truncated && !['findings', 'suppressed'].includes(reason);
const detailCut   = reason === 'findings';   // 有 totalFindings，说确切数字
const folded      = suppressed > 0;          // 折叠，单独一条
```

> 这样做的好处：`truncated=true` 仍然如实反映「有东西没给全」（C-09 的「禁止静默截断」不破），
> 但**「命中数可能偏少」这句只挂在真的漏扫上**，用户不会被假警报训练成忽略横幅。

## 3. 新增规则清单

### 3.1 十个关注点：已有的、要加的、暂缓的

| 关注点 | 现有规则 | 结论 |
|---|---|---|
| Thread.sleep 固定等待 | `ui-hard-sleep`（`:73`，含 `waitForTimeout`/`setTimeout`） | **已有，跳过**。可选小修：`sleep(Duration.ofSeconds(3))`、`time.sleep(SECONDS)` 现在不命中 |
| 缺显式超时 | — | **新增 `ui-no-timeout`** |
| driver 未 quit | — | **新增 `ui-driver-no-quit`** |
| System.out 代替日志 | — | 新增 `ui-print-instead-of-log`，**建议暂缓**（实测误报压不住，见 §3.3） |
| 断言只断非空 | `assert-truthy-only`（`:172`） | **已有，跳过** |
| try-catch 吞异常 | — | **新增 `assert-swallow-catch`**（本次唯一 high） |
| 测试方法无断言 | `assert-no-assertion`（`:182`，**文件级**） | **已有，但只到文件级**：一个文件里有一条断言就放行 → 「方法级无断言」仍是缺口，列为下一轮候选，本轮不做（要按方法切块，正则做不准） |
| 随机数据未固定种子 | — | **新增 `assert-random-no-seed`** |
| URL 拼接未 encode | — | **新增 `ui-url-concat-param`** |
| JSON 断言用字符串比较 | — | **新增 `assert-json-string-compare`** |
| （额外）用例被静默跳过 | — | **新增 `assert-skip-leftover`** |
| （额外）断言顺序/魔法值 | — | 不做（与 `assert-status-only` 重叠，收益低） |

**规则表还有余量**：audit 现在 12 条，`scanRules.test.ts:27` 断言 `≥12 且 ≤30`；+7 条 = 19 条，合规。

**两条硬约束（改之前必须知道）**：
1. `scanRules.test.ts:36-37` 断言「分类集合恰好 `['assert','secret','ui']`」。**新增规则不得引入新 category**，
   否则这条测试直接红。若将来真要加 `log`/`code` 一类，必须同时改这条断言 + `scan-rules.js:53` 的
   `CODE_ONLY_RULE_RE = /^(?:ui|assert|cov)-/`（否则新前缀规则会去扫 `.md`，`t55` 的 README 误报重演）。
2. 所有新 id **只用 `ui-` / `assert-` 前缀** → 自动继承文档守卫（`.md/.txt` 不报），也自动落进现有三类。

### 3.2 七条建议纳入（每条都在 Java fixture 上实跑验证过命中）

> 「判定」一栏是要写进 `RULES` 的真实形态：`kind:'file'` 用 `detect(codeText)`（行号 0），
> 否则给 `pattern` / `negative` / `requires`（行级，行号 1-based）。所有 `codeText` **已经过 `stripComments`**，
> 规则里**不要**再自己剥注释。

#### R1 `ui-driver-no-quit` — 浏览器驱动未释放（medium / ui）

- 判定（file 级）：
  ```js
  detect: (code) =>
    /new\s+(?:Chrome|Firefox|Edge|Safari)Driver\s*\(|webdriver\.(?:Chrome|Firefox)\s*\(/.test(code) &&
    !/\.quit\s*\(|\.dispose\s*\(|driver\s*\.\s*close\s*\(/i.test(code)
  ```
- 为什么要报：`driver` 不 `quit` → 僵尸 chromedriver 进程堆积，CI 上几轮后端口/内存耗光，表现为「换台机器就好了」的 flaky。
- 命中样例（实跑命中，`line=0`）：
  ```java
  public class LoginTest {
    WebDriver driver = new ChromeDriver();
    @Test public void login() { driver.get("http://example.com/login"); }
  }
  ```
- 不命中对照（实跑 0 命中）：`@AfterMethod public void down() { driver.quit(); }` 同文件出现即放行。
- **误报风险：中**。驱动在**基类**里 `quit`（`extends BaseTest`）时本文件看不到 → 会误报。
  建议 `negative` 再放行 `extends\s+\w*(?:Base|BaseTest|AbstractTest)`；本仓库实测 **0 命中**
  （没有 Selenium 代码），所以这条**只能靠 fixture 证明，不能拿本仓库当覆盖证据**。
- 用例：≥5（正例 / 有 quit 反例 / 基类反例 / 注释里不命中 / `.md` 不命中）。

#### R2 `ui-no-timeout` — 请求/驱动缺显式超时（medium / ui）

- 判定（file 级）：
  ```js
  detect: (code) =>
    /\b(?:given\s*\(\s*\)|restTemplate\.|requests\.(?:get|post|put|delete)\s*\(|axios\.(?:get|post|put|delete)\s*\(|fetch\s*\()/.test(code) &&
    !/\btimeout\b|\.timeout\s*\(|readTimeout|connectTimeout|Duration\.of|page\.setDefaultTimeout/i.test(code)
  ```
- 为什么要报：默认无超时 = 服务端挂住时用例**无限等**，CI 上表现为「卡住不退出」，比失败更难查。
- 命中样例（实跑命中）：`Response r = given().when().post("/api/login");`
- 不命中对照（实跑 0 命中）：`given().timeout(5000).when().post(...)`；`axios.get(url, { timeout: 3000 })`。
- **误报风险：高**（三条实测证据）：
  ① 超时可能配在**基类/全局**（`RestAssured.config`、axios 实例默认值），单文件看不见 → 必误报；
  ② 本仓库实测 **58 个文件命中**，其中 `electron/ipc-api.js`（Node 网络代码，不是测试）、
     `src/utils/codegen/restassured.ts`（**代码生成模板**，它不写 timeout 是模板选择）都中招；
  ③ `.md` 里贴的 `requests.get(...)` 也命中——必须靠 `CODE_ONLY_RULE_RE` 的文档守卫挡（id 前缀 `ui-` 已满足）。
- 缓解：加 `requires` 测试标记（见 §4.2），UI 文案写清「**本文件内**看不到超时」，并允许用户关规则。
- 用例：≥5。

#### R3 `assert-swallow-catch` — 吞异常（high / assert）★ 本次唯一 high

- 判定（**必须 file 级**）：
  ```js
  detect: (code) =>
    /catch\s*(?:\([^)]*\))?\s*\{\s*\}|catch\s*(?:\([^)]*\))?\s*\{\s*[\w.]+\s*\.\s*printStackTrace\s*\([^)]*\)\s*;?\s*\}/.test(code)
  ```
  为什么不能写成行级：空 `catch` 常跨行
  （`} catch (Exception e) {\n}`），行级正则匹配不到；`stripComments` 后注释被抹成空，跨行结构只在
  `join('\n')` 的 `codeText` 上才成立（`scan-rules.js:367-379` 的 file 分支）。
- 为什么要报：`catch(Exception e){}` = 用例永远绿。这是**假通过**，比报错更危险（W7 已踩过同类「静默折叠」）。
- 命中样例（实跑命中）：`try { api.pay(order); } catch (Exception e) { }`、`catch (Exception e) { e.printStackTrace(); }`。
- 不命中对照（实跑 0 命中）：`catch (Exception e) { throw new AssertionError(e); }`。
- **误报风险：极高（未加作用域时）**：本仓库实测 **139 个文件命中** —— `scripts/ 61`、`src/ 42`、`electron/ 27`。
  都是应用/工具代码里合法的 `try{ fs.closeSync(fd) } catch {}`（`electron/ipc-scan.js:77` 自己就是）。
  **加测试作用域后降到 1 个文件**（§4.2）。所以这条规则**必须**带测试作用域，否则不能上线。
- 用例：≥5（含「应用代码里的 try/catch 不命中」这条最重要的反例）。

#### R4 `assert-random-no-seed` — 随机数据未固定种子（medium / assert）

- 判定（行级）：
  ```js
  pattern: /new\s+Random\s*\(\s*\)|Math\.random\s*\(\s*\)|\brandom\.(?:random|randint|choice|uniform)\s*\(/,
  negative: /seed\s*\(|setSeed|new\s+Random\s*\(\s*\d+\s*\)/
  ```
- 为什么要报：用例每次跑的数据不同 → 失败无法复现，「昨天红了今天绿」只能靠重跑碰运气。
- 命中样例（实跑命中，`line=2`）：`int n = new Random().nextInt(100);`
- 不命中对照（实跑 0 命中）：`Random rnd = new Random(20260101L);`、`random.seed(42)`。
- **误报风险：高（未加作用域时）**：本仓库实测 **23 个文件 / 43 处**，绝大多数是应用代码用
  `Math.random()` 生成 id（`electron/codelab-preview.js:87` `Date.now().toString(36)+Math.random()...`）。
  **加测试作用域后 0 命中**。
- 用例：≥4。

#### R5 `assert-json-string-compare` — JSON 用字符串比较（medium / assert）

- 判定（行级）：
  ```js
  pattern: /(?:assertEquals?|assertThat|toBe|toEqual|assertEqual)\s*\([^)\n]*["'`]\{\s*\\/,
  negative: /jsonPath|JSON\.parse|\.json\b|jsonDecode/i
  ```
  ⚠️ 这里 `\{\s*\\` 里的「反斜杠」是**实测抓出来的**：第一版写成 `["'`]\{\s*` 就命中
  `expect(applyVars('{{nope}}', 'a=1')).toBe('{{nope}}')` —— `{{` 前面也是 `{`。
- 为什么要报：`assertEquals("{\"code\":0}", body)` 会把字段顺序、空格、数字/字符串差异当失败，
  也会**掩盖**真正的业务断言（它只证明「整串相等」，说不清哪个字段不对）。
- 命中样例（实跑命中，`line=2`）：`assertEquals("{\"code\":0}", r.getBody().asString());`
- 不命中对照（实跑 0 命中）：`assertEquals(0, r.jsonPath().getInt("code"));`
- **误报风险：中**，两处真实边界：
  ① `src/utils/__tests__/apiVars.test.ts:52` `expect(readJsonPath(body,'data.list[0]')).toBe('{"id":7}')`
     是**故意**断言「取出来的是 JSON 串」——会被报，且 `negative` 里的 `jsonPath` 会放过它（当前写法偏保守，可接受）；
  ② 上一版宽松正则命中的 `'{{baseUrl}}/x'` 类模板串是纯误报（已用 `\{\s*\\` 收掉）。
- 用例：≥4。

#### R6 `ui-url-concat-param` — URL 拼接参数未 encode（medium / ui）

- 判定（行级；`Q` = 引号字符类 = 双引号 / 单引号 / 反引号 三选一）：
  ```js
  pattern: /Q[^Q]*\?(?:\w+=)?[^Q]*Q\s*\+\s*[A-Za-z_$]|\+\s*Q&[^Q]*Q/,
  negative: /encodeURI|URLEncoder|URLSearchParams|urlencode|UriComponentsBuilder/
  ```
- 为什么要报：`?q=" + kw` 里 `kw` 带 `&`、空格、中文就改变参数语义 —— 用例本身写错，问题却报在接口上。
- 命中样例（实跑命中）：`String url = BASE + "/api/search?q=" + kw + "&page=1";`；
  Python `url = BASE + "/api/search?q=" + kw`。
- 不命中对照（实跑 0 命中）：`+ URLEncoder.encode(kw, "UTF-8")`；`given().queryParam("q", kw)`。
- **误报风险：低但要目录守卫**：本仓库实测 3 命中，其中 `coverage/prettify.js:244`
  `aa.push("(?:" + W(ae) + ")")` 是**工具产物/压缩代码**里的纯误报（`coverage/` 不在 `SKIP_DIRS`）。
- 用例：≥4。

#### R7 `assert-skip-leftover` — 用例被静默跳过/只看一条（medium / assert）

- 判定（行级）：
  ```js
  pattern: /@\w+\s*\([^)]*enabled\s*=\s*false|@Ignore\b|@Disabled\b|\b(?:it|test|describe|suite)\.(?:skip|only)\s*\(|pytest\.mark\.skip/
  ```
  ⚠️ 第一版写成 `enabled\s*=\s*false` 就误报 `src/utils/__tests__/clipHistory.test.ts:51` 的
  `enabled = false;`（普通属性赋值）——必须限定在**注解括号内**。`.only` 同理：留下 `.only` 会让整条套件只跑一条。
- 为什么要报：`@Ignore` / `.skip` / `enabled=false` 留在提交里 = 覆盖率虚高，没人知道这条没跑。
- 命中样例（实跑命中，`line=1`）：`@Test(enabled = false)\npublic void oldCase() { }`。
- 不命中对照（实跑 0 命中）：`@Test public void t() { }`、`enabled = false;`（普通赋值）。
- **误报风险：低**（修正后本仓库 0 命中）。争议点：有人**故意**留 skip 并写注释说明，这条会报——
  文案里要写「若是有意跳过，请补 reason 或加白名单」。
- 用例：≥4。

### 3.3 一条建议暂缓：`ui-print-instead-of-log`（low / ui）

- 判定：file 级 `测试标记 && /System\.(?:out|err)\.print|\.printStackTrace\s*\(|\bconsole\.(?:log|error|warn)\s*\(/`
- 实测：**未加作用域 115 个文件命中**；**加测试作用域后 2 个**——但这 2 个（`src/utils/__tests__/assertions.test.ts`、
  `codelabArgs.test.ts`）恰好是**测试 console 捕获**的用例，天然会写 `console.log` → 仍是误报。
- 结论：**收益（排版噪音）远小于误报代价**，建议不进本轮。若一定要留，severity 设 `low` 且默认不勾。

## 4. 误报控制

### 4.1 三条实测出来的「必须做」

| 措施 | 不做的实测代价 |
|---|---|
| **测试作用域前置**（文件里得先像测试代码） | 三条规则合计 **277 个文件**误报（139 + 115 + 23）→ 加后 **3 个** |
| **文档守卫**（`CODE_ONLY_RULE_RE`，靠 id 前缀） | `.md` 里贴的示例代码会被当缺陷报（t55 的 README 误报就是这类） |
| **目录/产物守卫** | `run/`、`coverage/`、`*.min.js`、`app.asar.unpacked` 里的压缩代码会产生**没法读**的命中（snippet 是压缩后的一行，截 200 字符也没意义） |

### 4.2 测试作用域的**推荐写法**（一次判完，所有规则共享）

不要每条规则各跑一遍全文正则——file 级规则一旦多起来，1 MB 文件上就是「每条规则一次全文扫描」。
建议在 `matchRules` 里算一次：

```js
const TESTISH = /(?:@Test\b|@Before|@After|@ParameterizedTest|describe\s*\(|\bit\s*\(|\btest\s*\(|\bdef\s+test_|public\s+void\s+test\w+\s*\()/;
const TEST_PATH = /(?:^|\/)(?:test|tests|__tests__|spec)\/|[.\/](?:test|spec)\.\w+$|Test\.java$/i;
const isTest = TESTISH.test(codeText) && TEST_PATH.test(filePath);
```
（`filePath` 已是 POSIX 分隔符的相对路径，见 `ipc-scan.js:187`。）

实测效果（同一批 704 文件）：

| 规则 | 不加作用域 | 加作用域 |
|---|---|---|
| `assert-swallow-catch` | 139 文件 | **1** |
| `ui-print-instead-of-log` | 115 文件 | 2（仍误报，故暂缓） |
| `assert-random-no-seed` | 23 文件 | **0** |

作用域本身要能命中真实测试代码：`src/test/java/PayTest.java`、`@Test public void t()` 这类都判 `true`
（已在 fixture 上验过）。⚠️ 它也会漏掉「不在 `test/` 目录、文件名也不带 Test」的用例文件——这是**有意的**
取舍（漏报 < 误报，理由同 `scan-rules.js:32-40`），写进规则 `desc` 里让用户知道。

### 4.3 目录守卫（建议同时改 `SKIP_DIRS`，`ipc-scan.js:23`）

本仓库实测污染源：`run/resources/app.asar.unpacked/`（打包产物，含 `exceljs.min-*.js`：单文件 80 ms、
`Math.random`/`console.log` 上百处）与 `coverage/`（工具产物）。建议 `SKIP_DIRS` 增补 `run`、`coverage`；
或加一条路径 negative：`/(?:\.min\.|\.bundle\.|app\.asar\.unpacked)/`。
影响：本仓库 704 → 约 560 个文件（少扫的是产物，不是源码）。

```ts
const ids = (text, filePath = JAVA, ruleIds?) => matchRules(text, filePath, ruleIds).hits.map(h => h.ruleId);
const hit = (ruleId, text, filePath = JAVA) => ids(text, filePath).includes(ruleId);

describe('UI 自动化反模式（正例 / 反例）', () => {
  it('ui-hard-sleep：Thread.sleep 命中', () => { expect(hit('ui-hard-sleep', '...')).toBe(true); });
```

建议**新增 1 条结构断言**（防将来漂移）：

```ts
  for (const r of rulesOf('audit')) expect(r.id).toMatch(/^(?:ui|assert|sec)-/);
```

### 5.3 正则在大文件上的成本（实测）

| 场景 | 实测 |
|---|---|
| 704 文件 / 8.03 MB，同一进程里注册 24 条规则、**只跑 12 条** audit | **677 ms**（≈0.96 ms/文件） |
| 同上，**跑 20 条**（12 + 8 候选） | **795 ms**（≈1.13 ms/文件，**+118 ms / +17%**） |
| 最慢单文件 | **80 ms**（1 MB 压缩包 `exceljs.min-*.js`，200+ 处命中） |
| 病态输入：1 MB 单行 × 3 种 × 20 条规则 | **296 ms**（无灾难性回溯：所有候选正则都是线性贪婪，没有嵌套量词） |
| 折算到 `maxFiles=2000` 上限 | 20 条规则 ≈ **2.3 s**，距 60 s 超时 26 倍余量 |

> 两轮测量的进程状态不同：§1.2 的 **466 ms** 是「规则表里只有 16 条」时的干净数，上表的 677 ms 是
> 「表里注册了 24 条、只跑其中 12 条」——多出来的部分是**逐条 `wanted.has()` 的过滤开销**，不是匹配本身。
> 所以**只看上表内部的 677 → 795 增量（+118 ms / +17%）**，它才是「新增 8 条规则」的真实代价。

**复用 `stripComments`（`scan-rules.js:10-12/275-327`）的三条纪律**：
1. **不要自己剥注释**。`matchRules` 已经给你 `codeLines`（行数一致）与 `codeText`；再剥一遍会把
   `"https://a"` 里的 `//` 当成注释起点，`sec-hardcoded-url` 这类规则会永远不命中（`:266-271` 的坑）。
2. **要行号 → 用行级 `pattern`**；**要跨行结构（空 catch / 方法体）→ 用 file 级 `detect`，行号只能记 0**。
   不要为了行号把 file 级结构硬写成行级正则（会漏掉跨行写法，正是 §3.2 R3 的坑）。
3. **file 级 `detect` 是全文正则**，条数要克制：现在 5 条 file 级（2 旧 + 3 新）。再多就该把
   「测试作用域」提成一次共享布尔（§4.2），否则 1 MB 文件上每条规则各扫一遍全文。
